# Mortarium AI — стандарт инженерии LLM и эффективности

**Статус:** инженерный стандарт  
**Применяется к:** Mortarium AI, RAG, агентам LangGraph, инструментам MCP и всем настроенным LLM-провайдерам  
**Приоритеты:** безопасность и корректность → изоляция tenant → надёжность → качество → задержка и стоимость

Этот стандарт рассматривает эффективность использования токенов как архитектурную задачу. Он не ставит целью минимизировать число токенов любой ценой. Цель — сократить ненужную работу моделей, сохранив доказательства, клинические предупреждения, цитаты и требования к проверке человеком.

## 1. Проектирование контекста

Каждый вызов модели должен получать только информацию, необходимую для конкретного шага.

- Стабильные системные инструкции и схемы инструментов должны оставаться неизменными; данные конкретного запроса размещайте позже в prompt.
- Не дублируйте текст политик в сообщениях пользователя, найденных чанках или результатах инструментов.
- Ограничивайте объём памяти диалога. Предпочитайте краткую периодически обновляемую сводку и ограниченное окно последних сообщений неограниченной стенограмме.
- Считайте ввод пользователя, найденные документы, результаты MCP и вывод провайдера недоверенными данными.
- Никогда не удаляйте противопоказания, единицы дозировки, уточнения о конкретном пациенте, метаданные источников или предупреждения безопасности только ради соблюдения token budget.
- Не передавайте модели генерации целые исходные документы, если достаточно релевантных фрагментов, доступ к которым разрешён.

## 2. Бюджеты retrieval и RAG

Ограничения RAG должны настраиваться и оцениваться на размеченном наборе поиска. Нельзя считать, что один фиксированный Top-K или размер чанка оптимален для всех типов документов и языков.

Следующие параметры RAG сейчас передаются из `RAGSettings` в активный конструктор `LangGraphRAG`:

| Параметр | Переменная окружения | Текущее значение по умолчанию | Назначение |
|---|---|---:|---|
| `top_k` | `RAG_TOP_K` | 10 | Число кандидатов для каждого поискового запроса/фильтра |
| `max_context_docs` | `RAG_MAX_CONTEXT_DOCS` | 12 | Максимум уникальных кандидатов после дедупликации для оценки |
| `max_rewrites` | `RAG_MAX_REWRITES` | 2 | Максимум циклов переписывания поискового запроса |
| `max_query_variations` | `RAG_MAX_QUERY_VARIATIONS` | 2 | Число вариантов запроса, запрашиваемых у transformer |
| `enable_multi_query` | `RAG_ENABLE_MULTI_QUERY` | true | Включает вызовы модели для расширения запроса |
| `enable_hyde` | `RAG_ENABLE_HYDE` | true | Включает вызов модели HyDE |

Следующие настройки объявлены, но не являются действующими параметрами текущего runtime: `RAG_RERANK_TOP_N` (reranker не внедрён), `RAG_RRF_K` (используется значение метода hybrid search по умолчанию), `RAG_ENABLE_CONTEXTUAL_COMPRESSION` (compression всегда присутствует в графе), `RAG_DEFAULT_LANGUAGES` (пути ingestion используют отдельные значения по умолчанию), `RAG_MAX_CHUNK_TOKENS` и `RAG_CHUNK_OVERLAP` (Celery task использует конфигурацию конкретной задачи с жёстко заданными значениями по умолчанию). Не обещайте, что изменение этих переменных окружения меняет поведение runtime, пока связка не реализована и не покрыта контрактными тестами.

Для управления бюджетом токенов используются `AI_TOKEN_MAX_INPUT_TOKENS` (по умолчанию 6000), `AI_TOKEN_MAX_OUTPUT_TOKENS` (по умолчанию 500) и `AI_TOKEN_SAFETY_MARGIN_TOKENS` (по умолчанию 256). Лимит входа проверяется предварительно. Лимит выхода остаётся настроенной целевой величиной, пока адаптер каждого провайдера явно не сопоставит его с собственным параметром генерации. Значения по умолчанию сохраняют текущее поведение retrieval. Настраивайте их только с помощью оценок качества поиска и ответов. Меньший Top-K не всегда лучше, если из него исключаются клинически важные доказательства.

Последовательность операционной настройки:

1. Подготовьте размеченный набор оценки для каждого поддерживаемого языка и workflow.
2. Измерьте recall@K, precision@K, корректность цитирования, groundedness и поведение при отсутствии ответа.
3. Постепенно уменьшайте ограничения retrieval и контекста.
4. Повторно запускайте регрессионную оценку перед развёртыванием изменённых лимитов.
5. Независимо от бюджета сохраняйте обязательные фильтры tenant, аптеки, страны, пациента и уровня доступа.

## 3. Маршрутизация моделей

- Для CRUD, арифметики, валидации, разрешений и простых поисковых операций используйте детерминированный код приложения; не вызывайте LLM для таких операций.
- Направляйте лёгкую классификацию и преобразование запроса быстрой модели только в том случае, если её результат проходит валидацию.
- Для обычных ответов с опорой на источники используйте настроенную основную модель.
- Вопросы с высоким риском или сложные клинические вопросы передавайте назначенной более мощной модели и/или фармацевту.
- Маршрутизация никогда не должна обходить авторизацию, guardrails, требования к доказательствам или проверку человеком.
- Записывайте выбранную модель и причину выбора в метрики с ограниченной кардинальностью; никогда не используйте ID пользователя, пациента, аптеки, prompt или документа в метках метрик.

## 4. Проектирование prompt и ответов

- Используйте краткие prompts, ориентированные на конкретную задачу, с явным контрактом результата.
- Для результатов, обрабатываемых машиной, предпочитайте структурированные схемы и проверяйте данные до использования.
- Устанавливайте поддерживаемые провайдером ограничения выходных токенов, если адаптер предоставляет совместимый параметр. Не предполагайте, что параметр одного провайдера работает у всех.
- Не просите модель повторять вопрос или воспроизводить текст найденного источника.
- Не запрашивайте скрытые рассуждения. Просите краткий вывод, релевантные доказательства, цитаты и указание неопределённости.
- Сохраняйте точные ID цитат и связь между найденными чанками и итоговым ответом API.

## 5. Кеширование

Кеширование — оптимизация, а не источник истины. Семантический кеш ответов Mortarium по умолчанию отключён, если доверенная серверная политика явно не помечает запрос как безопасный; запросы с областью пациента никогда не подходят для него. Точные записи кеша ограничены tenant/user, включают соответствующие измерения версии данных, если они переданы, и по умолчанию имеют TTL один час. `force_fresh` обходит чтение и запись в streaming и non-streaming путях API.

- Точное кеширование prompt допустимо, если полная идентичность запроса представлена в ключе кеша.
- Ключи кеша должны включать область аутентифицированного пользователя и аптеки, а также каждый атрибут контекста, способный изменить ответ (например, пациента, страну, язык, разрешения и соответствующие идентификаторы данных/версий).
- Никогда не разделяйте кешированные ответы, специфичные для пациента или зависящие от разрешений, между пользователями или аптеками.
- Не используйте семантическое повторное применение ответов на вопросы о дозировке, взаимодействиях, противопоказаниях, рекомендациях конкретному пациенту и другие вопросы безопасности, если отдельная проверенная архитектура не докажет эквивалентность и актуальность.
- Для изменяемых операционных данных используйте короткий явный TTL; инвалидируйте кеш при изменении соответствующих источников.
- При cache miss или отказе кеша используйте обычный авторизованный путь выполнения.
- Не кешируйте ошибки, заблокированные запросы или ответы с недостаточными доказательствами как успешные ответы.

Кеширование prompt на стороне провайдера отличается от кеша ответов приложения в Redis. Используйте его только при поддержке провайдера; сохраняйте стабильные префиксы prompt и измеряйте фактическое использование cache-read/cache-write.

### Хранение памяти диалога и границы доверия

Память Mortarium имеет три логических уровня: окно последних сообщений, скользящая сводка и явно сохранённые эпизодические факты. Недавнее окно уплотняется после успешной суммаризации; если суммаризация недоступна или завершается ошибкой, исходные реплики сохраняются, и список может расти до истечения настроенного TTL Redis. Идентификаторы сессий должны формироваться на аутентифицированной границе API и быть ограничены tenant, пользователем и диалогом.

- Скользящая сводка является неполной и не должна считаться авторитетной записью клинических деталей.
- До удаления суммаризированных реплик из активного окна prompt сохраняйте их исходные сериализованные сообщения в архиве Redis, ограниченном сессией и имеющем тот же TTL.
- Не обрезайте исходные реплики до успешного завершения суммаризатора. Если суммаризация недоступна, завершается ошибкой или возвращает пустое содержимое, сохраняйте исходные реплики и пропускайте уплотнение.
- Вспомненные сводки и эпизодические факты — недоверенный исторический контекст, а не системные инструкции или проверенные клинические данные. Повторно проверяйте клинические утверждения по актуальным разрешённым источникам.
- При суммаризации считайте содержимое стенограммы недоверенным вводом: игнорируйте встроенные инструкции и сохраняйте явные единицы дозировки, противопоказания, аллергии, предупреждения, неопределённость и происхождение данных, если они присутствуют.
- Архив — краткосрочное средство восстановления/аудита, а не долгосрочная клиническая запись с поиском. Он не воспроизводится автоматически в prompts. Для включения извлечения из архива требуется отдельная авторизованная архитектура.
- Не извлекайте и не сохраняйте автоматически клинические факты конкретного пациента как эпизодическую память без проверенной политики согласия, авторизации, происхождения, хранения и удаления.

## 6. Ограничения выполнения Agent и MCP

- Ограничивайте рекурсию графа, число итераций агента, вызовы инструментов, timeout каждого инструмента, retries и общий deadline запроса.
- Предоставляйте только инструменты, необходимые для текущей задачи и области авторизации вызывающего пользователя.
- Проверяйте аргументы инструментов типизированными схемами и обеспечивайте авторизацию на границе приложения.
- Возвращайте компактные результаты инструментов: выбранные поля, стабильные ID, статус и происхождение данных. Не передавайте модели целые записи БД или необработанные логи.
- Не повторяйте неидемпотентные операции, пока не предусмотрена стратегия идемпотентности.
- Для значимых операций записи требуйте явного подтверждения, а для клинических решений, требующих профессионального суждения, — проверки человеком.

## 7. Наблюдаемость и учёт стоимости

Фиксируйте, если провайдер предоставляет такие данные:

- входные, выходные и общие токены, модель/провайдер;
- токены чтения/записи кеша или cache hit/miss;
- число кандидатов retrieval и итоговый размер контекста;
- число вызовов модели, шагов графа и вызовов инструментов MCP;
- задержку по этапам и общую задержку запроса;
- результаты success, refusal, no-evidence и fallback.

Авторитетным количеством считайте usage, сообщённый провайдером. Если используется локальная оценка tokenizer, обозначайте её как приблизительную и указывайте версию tokenizer/model. Не выводите точное число токенов из количества символов.

Метки Prometheus должны сохранять низкую кардинальность. Для диагностики отдельных запросов используйте логи/трассы с контролем доступа; по умолчанию никогда не записывайте секреты, необработанные данные пациентов, полные prompts или полные найденные документы.

Отслеживайте стоимость каждого workflow и модели, если известны тарифы. Оптимизируйте стоимость с учётом качества, а не только число токенов.

## 8. Критерии оценки

Перед изменением prompt, модели, стратегии chunking, лимита retrieval, политики кеширования или правила маршрутизации запускайте репрезентативные тесты, охватывающие:

- полноту retrieval и изоляцию tenant;
- корректность ответов и groundedness;
- точное сохранение цитат на источники;
- многоязычное поведение;
- prompt injection в найденном содержимом;
- противопоказания, единицы дозировки, взаимодействия и обработку неопределённости;
- сценарии отсутствия доказательств и отказа провайдера;
- изоляцию кеша и поведение с устаревшими данными;
- задержку и бюджеты токенов/стоимости.

Изменение, сокращающее число токенов, но ухудшающее безопасность, полноту поиска, цитирование или качество ответов, не должно приниматься.

## 9. Профили развёртывания

- Не храните веса LLM в Git-репозитории. Идентификаторы моделей и конфигурацию развёртывания храните под контролем версий; credentials — в менеджере секретов платформы.
- Отделяйте inference от приложения FastAPI, если хост приложения не обеспечивает достаточные ресурсы RAM/VRAM и CPU/GPU.
- Не используйте GitHub Actions или временное development-окружение как постоянный inference-сервис.
- Выполняйте нагрузочное тестирование фактического профиля развёртывания; размер локальной модели на диске не равен требуемой RAM/VRAM во время выполнения.
- Делайте выбор провайдера/модели явным и наблюдаемым, чтобы fallback не мог незаметно изменить характеристики безопасности или качества.

## 10. Статус реализации (аудит ветки main)

Следующие утверждения описывают исходный код и конфигурацию на проверенной ревизии `main`. Объявленная настройка, точка расширения или unit-тест не доказывают, что функция активна или клинически валидирована.

Реализовано в runtime:

- графы Pharmacist Agent и RAG на LangGraph с явной настройкой PostgreSQL checkpointer;
- аутентифицированный контекст аптеки, проверка членства пациента на границе AI API и fail-closed фильтры аптеки в pgvector retrieval;
- гибридный векторный и полнотекстовый поиск PostgreSQL с reciprocal-rank fusion;
- сохранение исходного запроса, настраиваемые переключатели multi-query/HyDE, ограниченные циклы переписывания, оценка документов, контекстное сжатие, предварительная проверка бюджета входных токенов генерации и валидация ID цитат;
- обнаружение MCP-инструментов с фильтрацией по ролям и доверенная авторизация в контексте запроса; запись через MCP запрещена, пока не настроен доверенный verifier подтверждения;
- память диалога Redis с версионируемыми HMAC-ключами namespace и TTL семь дней;
- HMAC-идентификаторы checkpoint для Pharmacist Agent;
- offline-адаптер Ragas 0.4.3 и проектные помощники фармацевтической оценки, изолированные от production-зависимостей.

Известные пробелы реализации:

- Память диалога и идентификаторы потоков обоих graph checkpoint не привязаны к ID пациента. ID потока checkpoint RAG также представляет собой открытый составной идентификатор pharmacy/user/session, в отличие от HMAC-идентификатора checkpoint агента и ключа памяти. Это задачи устранения проблем изоляции пациента/конфиденциальности, а не только оговорки документации.
- Русский язык отсутствует в текущих базовых настройках core, RAG и ingestion. Поддержка RU/EN evaluator не доказывает качество RU retrieval.
- В текущий runtime не внедрён конкретный reranker. Настройка `RAG_RERANK_TOP_N` объявлена, но не используется.
- `RAG_ENABLE_CONTEXTUAL_COMPRESSION` объявлен, но не подключён; compression выполняется всегда. `RAG_RRF_K`, `RAG_DEFAULT_LANGUAGES`, `RAG_MAX_CHUNK_TOKENS` и `RAG_CHUNK_OVERLAP` также требуют подключения/контрактной проверки.
- Значения confidence и safety-score API — константы, зависящие от предупреждений, а не калиброванные метрики.
- Celery task является активным API-путём ingestion. Отдельный `IngestionOrchestrator` создаётся, но не используется проверенным API-путём и явно не проставляет те же канонические метаданные tenant перед upsert.
- Тесты offline-evaluator для адаптера Ragas подменяют классы метрик; CI также проверяет импорт закреплённого collections API. Это не является измеренным запуском LLM-judge или клинической валидацией фармацевтом.
- Хранение/удаление payload checkpoint, истечение резервных копий и полные меры жизненного цикла PHI требуют отдельной операционной проверки для каждого deployment.
- Live retrieval RU/EN, клиническое качество ответов, семантическая корректность цитат, latency и стоимость production-модели/провайдера не установлены этим статическим аудитом.

Не закрывайте эти пробелы только на основании успешного static/unit CI. Текущие замечания и release gates отслеживаются в [аудите архитектуры Mortarium AI / RAG](./rag_architecture_audit.md).
