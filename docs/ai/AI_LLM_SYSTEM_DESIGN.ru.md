# Проектирование системы Mortarium AI / LLM

**Статус:** текущая реализация и явно обозначенные проектные требования.

## 1. Роль системы

Mortarium — встроенный в Pharmaviyum ассистент поддержки принятия решений для фармацевта. Он помогает сотрудникам находить информацию, суммировать разрешённый контекст и ориентироваться в рабочих процессах.

Mortarium не является системой учёта (system of record), заменой лицензированного специалиста, механизмом авторизации, детерминированным движком ценообразования/учёта запасов/платежей/отпуска или доказательством того, что конкретный препарат подходит пациенту.

Детерминированный код приложения отвечает за разрешения, расчёты, транзакционные изменения и нормативные ограничения. Результаты AI носят рекомендательный характер и должны быть ограничены подтверждающими данными.

## 2. Логическая архитектура

Путь запроса: аутентифицированный фармацевт → FastAPI AI API → проверка tenant/пациента → Agent Harness → ограниченная память Redis и prompt cache → маршрутизация моделей → агент фармацевта LangGraph → LangGraph RAG и/или MCP registry с фильтрацией по ролям → обоснованный источниками ответ с предупреждениями → проверка фармацевтом.

Это логические компоненты приложения, а не отдельные deployable-сервисы.

## 3. Жизненный цикл запроса

1. FastAPI аутентифицирует пользователя.
2. API определяет разрешённый контекст аптеки.
3. Если выбран пациент, API проверяет, что пациент активен и относится к этой аптеке.
4. Доверенный контекст формируется из серверной идентичности и проверенных полей запроса.
5. Agent Harness загружает ограниченную память, применяет входные контроли и проверяет допустимые записи кеша.
6. Маршрутизатор моделей выбирает настроенную модель для задачи.
7. Агент LangGraph решает, отвечать ли на основе контекста, запускать retrieval или запрашивать разрешённый MCP-инструмент.
8. RAG извлекает данные с фильтрацией по tenant, оценивает их, при необходимости переписывает запрос в пределах заданного бюджета, сжимает доказательства и формирует ответ с цитатами.
9. MCP-инструменты выполняются только с доверенным контекстом авторизации запроса и фильтрацией по ролям.
10. Перед возвратом ответа запускаются выходные guardrails.
11. Фармацевт проверяет ответ и сохраняет ответственность за профессиональное решение.

Точные схемы запросов и ответов определены в коде и сгенерированной OpenAPI-схеме; здесь они не дублируются.

## 4. Agent Harness

Harness отвечает за сквозные входные/выходные guardrails, ограниченную память диалога, оркестрацию prompt/cache, маршрутизацию моделей, выполнение/потоковую передачу агента, формирование структурированного ответа и телеметрию.

Память — это вспомогательный контекст, а не авторитетная медицинская запись пациента. Сводки памяти не должны переопределять актуальные проверенные данные пациента, состояние рецепта или исходные документы.

Идентификатор кеша должен включать каждое измерение контекста, способное повлиять на корректность или авторизацию. Никогда не переиспользуйте ответы с данными пациента между разными пациентами, tenant, пользователями или границами разрешений.

## 5. Агент LangGraph и RAG

Агент фармацевта и RAG являются отдельными процессами LangGraph. RAG использует ограниченное преобразование запроса, retrieval, оценку документов, сжатие, генерацию и guardrails.

Правила retrieval:
- Гибридный поиск объединяет полнотекстовый поиск PostgreSQL и поиск сходства pgvector.
- Фильтры включают контекст аутентифицированной аптеки.
- Для документов уровня пациента требуется явный фильтр пациента.
- Исходный запрос пользователя остаётся кандидатом retrieval; переформулировки только дополняют его.
- Названия препаратов, дозировки/сила, лекарственные формы и отрицания должны сохраняться.
- Результат HyDE — вспомогательный материал для поиска, а не проверенное доказательство.
- Извлечённые документы являются недоверенным вводом и никогда не становятся системной политикой.
- Стабильные source ID должны сохраняться при retrieval, сжатии и цитировании.

Не описывайте reranker как активный компонент, пока конкретная реализация не подключена и не протестирована. Аудит выявляет настройки, которые объявлены, но не все подключены к runtime; см. [аудит RAG](../rag_architecture_audit.md) и [стандарт инженерии LLM](../llm_engineering_standards.md).

## 6. Ingestion

Активный API ingestion path запускает Celery-задачи, авторизованные для tenant. Worker загружает/предварительно обрабатывает документы, добавляет tenant metadata, выполняет chunking, создаёт embeddings и сохраняет результат. Не предполагайте, что отдельный orchestrator обеспечивает те же метаданные и авторизацию, пока это не подтверждено тестами.

Задачи должны быть идемпотентными, ограниченными и безопасными для повторного запуска. Сохраняйте метаданные источника, юрисдикции, языка, версии и tenant.


Метаданные RAG с областью пациента используют текущий контракт `CanonicalMetadata`: `pharmacy_id` — обязательная граница аптеки/tenant; `access_level` принимает одно из значений `public`, `pharmacy` или `patient`; `patient_id` необязателен, кроме чанков уровня пациента, где он обязателен. Не вводите параллельное поле `tenant_id` без проверенной миграции. ID пациента проверяются сервером относительно аутентифицированной аптеки; им нельзя доверять, если они пришли из prompt или аргументов, сгенерированных моделью. Если пациент не выбран, чанки уровня пациента исключаются, а не сопоставляются через wildcard. Каждый этап retrieval, расширение parent/source и путь cache/state должны сохранять одну и ту же область доступа и работать по принципу fail closed. См. подробный контракт метаданных и обязательные тесты в [pipeline чанкинга](./chunking-pipeline.ru.md#11a-patient-scoped-metadata-and-retrieval-isolation).

## 6A. Фармацевтический pipeline чанкинга

Chunking — отдельная задача ingestion, а не просто универсальное разделение текста. Текущий `MedicalChunker` предоставляет эвристики медицинских заголовков, группировку по предложениям и рекурсивный fallback. Его лимит по умолчанию — 512 оценочных токенов с overlap 50. Это оценка на основе количества символов, делённого на четыре, а не точный подсчёт токенизатором модели. Текущая стратегия semantic группирует границы предложений; она не выполняет семантическую сегментацию на основе embeddings.

Целевая архитектура должна быть версионируемой и учитывать структуру: сохранять пути заголовков разделов, заголовки/строки таблиц, идентичность препарата, дозировку и единицы, лекарственную форму, путь введения, отрицания, условия, юрисдикцию, версию источника и якоря страниц. Parent-child retrieval и разбор с учётом таблиц являются целевыми возможностями; их нельзя описывать как готовые до реализации и покрытия тестами.

Каждый chunk должен сохранять происхождение источника и ту же доверенную область доступа аптеки/пациента, что и родительский документ. При расширении parent необходимо повторно применять фильтры авторизации. Повторная индексация должна публиковать проверенную новую ревизию индекса и сохранять возможность rollback, а не разрушительно заменять активный индекс.

Ревизии chunking оцениваются offline с помощью Ragas и детерминированных фармацевтических проверок: корректность цитат, сущности/дозировка/форма/путь введения препарата, отрицания, целостность таблиц, мультиязычный retrieval, актуальность и изоляция пациента/аптеки. Для оценки используются синтетические или деидентифицированные данные; оценки LLM-judge являются сигналами регрессии, а не клинической валидацией.

См. [Фармацевтический pipeline чанкинга Mortarium](./chunking-pipeline.ru.md): там описаны границы текущей реализации, контракт метаданных, эксперименты настройки, версионирование, acceptance tests и карта кода.

## 7. Граница MCP-инструментов

Registry фильтрует инструменты по ролям; выполнение требует доверенного контекста авторизации, привязанного к запросу.

- Модель может предложить вызов инструмента; сервер решает, разрешён ли он.
- Никогда не доверяйте tenant/user/role ID, переданным внутри аргументов, сгенерированных моделью.
- Проверяйте аргументы по строгим схемам.
- Для операций записи используйте детерминированные доменные сервисы.
- Операции записи требуют явной авторизации и отдельно проверенного процесса подтверждения; намерение модели не является подтверждением.
- Возвращайте только минимально необходимые данные.
- Записывайте ограниченные метаданные результата инструмента без чувствительных аргументов/результатов.

Документированные на данный момент инструменты аптечных операций доступны только для чтения. Не делайте вывод о наличии возможности записи лишь из факта существования MCP.

## 8. Изоляция контекста пациента

PR #287 объединил реализацию session namespace и checkpoint namespace с областью пациента в `main` (merge commit `4d761990b31ef3aa78327dda1380689f2d094e8f`). Проверки RAG Safety Regression, Unit Tests и Integration Tests прошли на merge commit.

Это не доказывает активацию в production или завершение staging release gate. Обязательный end-to-end тест остаётся открытым: повторно использовать одну client session для пациента A → пациента B → отсутствия пациента в синхронном и потоковом режимах, включая PostgreSQL checkpoint persistence и Redis memory. Пока результат такого теста не подтверждён и релиз явно не развернут, нельзя утверждать, что изоляция контекста пациента доказана в production.

Обязательный инвариант: аптека + аутентифицированный пользователь + пациент (включая явное отсутствие пациента) + client session.

Изменения namespace требуют плана совместимости, хранения и rollback. См. [ADR-0003](../adr/ADR-0003-patient-scoped-ai-state.md) и [PR #287](https://github.com/Akil-Ibrahim/Pharmaviyum-ERP/pull/287).

## 9. Фармацевтическая оценка

Ragas — offline evaluator, а не зависимость production request path. Общие RAG-метрики необходимо сочетать с детерминированными метриками, специфичными для аптеки.

| Измерение | Метод оценки |
|---|---|
| Корректность цитат | Действительный source ID и entailment на уровне утверждения |
| Точность сущностей препарата | Точное название, дозировка/сила и лекарственная форма |
| Сохранение отрицаний | Правильная полярность положительных/отрицательных утверждений |
| Доля клинических галлюцинаций | Неподтверждённые клинические утверждения / все размеченные клинические утверждения |
| Изоляция контекста пациента | Отсутствие источников или состояния другого tenant/пациента |
| Мультиязычный retrieval | Recall эталонных источников и качество ответов по языкам, особенно английскому и русскому |
| Воздержание от ответа | Безопасное отсутствие ответа при недостаточных, устаревших или противоречивых доказательствах |

Фиксируйте dataset, ревизию corpus/index, язык, модель, prompt, версию evaluator, размер выборки и результаты экспертной adjudication. Оценки LLM-judge являются сигналами регрессии, а не клинической валидацией. Пороговые значения требуют квалифицированной проверки.

См. [оценку Ragas](./ragas-pharmaceutical-evaluation.ru.md), [выявление галлюцинаций и red-team](./hallucination-detection-and-red-team.ru.md) и [требования к benchmark](../devops/ENGINEERING_BENCHMARK_REQUIREMENTS.md). Стратегия оценки объединяет детерминированные фармацевтические проверки, offline-измерения Ragas и DeepEval, необязательную оценку согласованности HHEM и adversarial-тестирование Promptfoo. Сами по себе эти evaluators не являются production safeguards; runtime decision gate должен быть реализован и протестирован отдельно.

## 10. Наблюдаемость и конфиденциальность

Используйте ограниченные spans/metrics для длительности запроса и графа, количества retrieval, числа переписываний, кодов предупреждений, задержки/класса ошибок провайдера, имени/результата MCP-инструмента и статуса ingestion-задач.

Не записывайте prompts, completions, идентификаторы пациентов, данные рецептов, извлечённый клинический текст, ключи/значения Redis или исходные аргументы MCP. Автоматическая instrumentation FastAPI, SQLAlchemy и HTTPX включается только opt-in в development/test после проверки редактирования чувствительных данных; автоматическая instrumentation команд Redis остаётся отключённой.

См. [политику OpenTelemetry](../observability/opentelemetry.ru.md).

## 11. Надёжность и контроль затрат

- Ограничивайте рекурсию графа, число переписываний, параллелизм retrieval и время выполнения.
- Используйте явные тайм-ауты и ограниченные повторы с jitter.
- Применяйте token budgets, не удаляя предупреждения и единицы дозировки.
- Кешируйте только тогда, когда безопасность области доступа и актуальность подтверждены.
- Обеспечивайте независимую деградацию необязательного AI от POS и основного ERP.
- Рассматривайте квоты провайдера, rate limits и сбои как ожидаемые ситуации.
- Избегайте скрытых вызовов модели в детерминированных CRUD-процессах.

## 12. Контрольный список модели угроз

- [ ] Межtenantный retrieval и вызов инструментов.
- [ ] Повторное использование памяти, кеша и checkpoint между пациентами.
- [ ] Prompt injection в загруженных/извлечённых документах.
- [ ] Подмена аргументов инструментов и повышение привилегий.
- [ ] Неподтверждённые цитаты и галлюцинированные утверждения.
- [ ] Подмена дозировки/формы препарата.
- [ ] Потеря отрицаний при переписывании или сжатии.
- [ ] Утечка PHI через traces, logs, caches или evaluation data.
- [ ] Неограниченные циклы графа, размер документов или fan-out инструментов.
- [ ] Устаревший corpus, неверная юрисдикция или несовпадение языка.
