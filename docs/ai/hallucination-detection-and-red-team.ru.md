# Выявление галлюцинаций Mortarium и оценка безопасности AI

[English](hallucination-detection-and-red-team.md) · **Русский**

## Назначение

Документ описывает средства оценки, которые выявляют неподтверждённые утверждения модели, проверяют поведение при adversarial-воздействиях и предотвращают передачу фармацевту небезопасных ответов. Он дополняет, но не заменяет [фармацевтическую оценку Ragas](./ragas-pharmaceutical-evaluation.ru.md).

**Важная граница:** инструменты оценки дают сигналы качества. Ни один из них не доказывает, что клинический ответ безопасен, корректен или подходит конкретному пациенту. Авторизация и детерминированные аптечные правила приложения должны работать по принципу fail-closed; за профессиональные решения отвечает фармацевт.

## Определения инструментов и назначение

| Инструмент | Определение | Применение в Mortarium | Граница выполнения |
|---|---|---|---|
| **Ragas** | Фреймворк оценки Retrieval-Augmented Generation (RAG). | Измеряет faithfulness, answer relevancy, context precision и context recall; сравнивает изменения retrieval/prompt/model на версионируемом датасете. | Offline-оценка и CI-регрессии. Не входит в production request path. |
| **DeepEval** | Фреймворк LLM-оценки с тест-кейсами в стиле pytest и метриками, включая hallucination и faithfulness. | Независимо проверяет, подтверждаются ли утверждения найденным контекстом; добавляет повторяемые LLM/agent-регрессии и фармацевтические критерии. | Изолированная среда оценки. Judge-модель и credentials настраиваются явно; production credentials нельзя использовать неявно. |
| **Vectara HHEM (Hughes Hallucination Evaluation Model)** | Предварительно обученный классификатор, оценивающий фактическую согласованность источника/контекста с сгенерированным утверждением или резюме. | Даёт дополнительный модельный сигнал groundedness на уровне предложения/утверждения и помогает отмечать неподтверждённые фрагменты для проверки или отказа от ответа. | Необязательный изолированный сервис оценки. Не production-зависимость до проверки ресурсов, задержки, версии модели, порога и совместимости с Python/runtime. |
| **Promptfoo** | CLI для оценки prompts/LLM и red-team тестирования, запускающий воспроизводимые кейсы и adversarial-проверки против приложения или model endpoint. | Проверяет prompt injection в найденных документах, jailbreak, попытки утечки данных, небезопасные запросы о лекарствах, неправильное использование инструментов и мультиязычные атаки. | Запуск вручную или по расписанию против выделенной non-production среды. Не направлять red-team сканирование на production-данные пациентов. |
| **Pytest + детерминированные фармацевтические проверки** | Обычные автоматические тесты и rule-based assertions. | Проверяют точное название/дозировку/форму препарата, полярность отрицаний, citation IDs, tenant/patient scope, схемы и безопасный отказ. | Быстрый CI gate. Критические инварианты не должны зависеть от LLM judge. |

### Чего инструменты не доказывают

- Ragas и DeepEval используют статистические и/или LLM-оценки. Результаты зависят от датасета, judge-модели, prompt и версии оценщика.
- HHEM оценивает согласованность ответа с контекстом, но не проверяет авторитетность, актуальность, применимость к юрисдикции или клиническую корректность самого источника.
- Promptfoo ищет слабые места с помощью настроенных атак. Чистый отчёт не доказывает отсутствие всех атак и режимов отказа.
- Валидный citation ID не доказывает, что источник логически подтверждает утверждение. Для этого нужна проверка связи claim-to-source.
- Высокие агрегированные оценки никогда не компенсируют нарушение изоляции пациента, неверную дозировку/форму, потерю отрицания или неподтверждённое клиническое утверждение высокого риска.

## Жизненный цикл оценки

1. **Создать доверенный контекст.** API аутентифицирует фармацевта, определяет область аптеки и проверяет выбранного пациента. Аргументы модели не могут устанавливать личность или права.
2. **Получить доказательства.** LangGraph RAG извлекает только документы, разрешённые текущей областью аптеки/пациента. Сохраняются source IDs, версия источника, язык и юрисдикция.
3. **Сгенерировать кандидат ответа.** Модель может делать только утверждения, ограниченные доказательствами. Найденный текст является недоверенным вводом, а не системной политикой.
4. **Извлечь и проверить утверждения.** Ответ разбивается на независимо проверяемые фактические утверждения. Каждая цитата проверяется по указанному источнику; одного существования ID недостаточно.
5. **Запустить сигналы оценки.** Ragas и DeepEval измеряют groundedness/relevance; HHEM может дать независимый сигнал согласованности на уровне предложения; детерминированные проверки валидируют фармацевтические сущности, отрицания и область доступа.
6. **Применить decision gate.** Политический слой, а не LLM, решает, можно ли вернуть кандидат ответа.
7. **Записать безопасную telemetry.** Записываются версии evaluator/model/dataset, агрегированные оценки, коды решения и длительность. Нельзя логировать prompts, completions, идентификаторы пациентов, рецепты или найденный клинический текст.

## Политика принятия решения

| Результат | Значение | Требуемое поведение |
|---|---|---|
| **ALLOW** | Все обязательные детерминированные проверки пройдены, поддержка источниками соответствует откалиброванным порогам. | Вернуть ответ с цитатами и обычной формулировкой рекомендательной поддержки для фармацевта. |
| **WARNING** | Есть некритичная неопределённость, например неполные доказательства или низкая уверенность в некритичном утверждении. | Явно обозначить ограничение и показать источники; не выдавать неопределённость за факт. |
| **ABSTAIN** | Доказательства отсутствуют, противоречат друг другу, устарели, не подходят юрисдикции или критическое утверждение не подтверждено. | Не придумывать рекомендацию. Объяснить, каких доказательств не хватает, и запросить проверку фармацевта. |
| **BLOCK** | Нарушение авторизации, межпациентские/межаптечные данные, небезопасный вызов инструмента, некорректные критические сведения о препарате или другое жёсткое нарушение политики. | Не возвращать небезопасный контент и не выполнять действие. Создать обезличенное событие безопасности. |

Одного числового балла недостаточно для решения о безопасности лекарственной рекомендации. Пороговые значения калибруются на наборе, проверенном фармацевтом, и версионируются вместе с evaluator, моделью и датасетом.

## Покрытие фармацевтических тестов

Golden dataset должен использовать синтетические или надлежащим образом обезличенные примеры и охватывать:

- название препарата, действующее вещество, дозировку/концентрацию, форму, путь введения и единицы;
- противопоказания, взаимодействия, аллергии и утверждения о дозировках;
- сохранение отрицаний и условных формулировок;
- entailment цитат на уровне утверждений и актуальность источников;
- противоречивые документы, отсутствие доказательств и безопасный отказ;
- retrieval и ответы на русском и английском с отдельной отчётностью;
- prompt injection и вредоносные инструкции в найденных документах;
- авторизацию вызовов инструментов, least privilege и подмену аргументов;
- изоляцию между аптеками и пациентами для retrieval, memory, cache и checkpoints.

Никогда не отправляйте идентификаторы пациентов, текст рецептов, записи пациентов или другую PHI сторонним LLM judges и red-team провайдерам. Используйте синтетические fixtures и обезличенные идентификаторы кейсов.

## Интеграция в репозиторий и текущий статус

- **Ragas:** указан в `requirements-eval.txt`; текущий CI проверяет импорт/API, контракт фармацевтических метрик и golden dataset. Это offline-оценка, а не production-фильтр ответов.
- **DeepEval:** закреплён как изолированная зависимость оценки в `requirements-eval-deepeval.txt`. CI выполняет import/API smoke check. Полный hallucination suite с judge требует явно настроенной evaluation-модели и подготовленных кейсов.
- **HHEM:** описан как дополнительный model-based evaluator. Модель не устанавливается в production image FastAPI и пока не является live request-path gate. Перед включением проверьте revision, лицензию, совместимость runtime/Python, CPU/GPU, latency и порог, проверенный фармацевтом.
- **Promptfoo:** предназначен для red-team тестирования по требованию против отдельного non-production endpoint. Конфигурация target и credentials намеренно не выдумываются; production endpoint и secrets в репозитории не зашиты.
- **Decision gate:** документ описывает целевую политику. Не утверждайте, что она действует в Production, пока код приложения не обеспечивает её выполнение, а integration tests не подтверждают ALLOW/WARNING/ABSTAIN/BLOCK.

### Изолированная среда DeepEval

Устанавливайте только в среде оценки:

```bash
uv pip install --python .venv-eval/bin/python -r requirements-eval-deepeval.txt
```

Используйте отдельную evaluator-модель, явно заданную для тестового запуска. Не загружайте evaluation cases в hosted reporting service без проверки конфиденциальности, хранения, региона и договорных ограничений.

### Red-team workflow Promptfoo

Используйте сохранённую [конфигурацию Promptfoo](../../promptfooconfig.yaml) против выделенного non-production deployment. Перед запуском задайте переменные окружения: `MORTARIUM_EVAL_TARGET_URL` (полный URL, заканчивающийся на `/api/v1/ai/query`), `MORTARIUM_EVAL_API_TOKEN` (bearer token тестового пользователя с минимальными правами), `MORTARIUM_EVAL_PHARMACY_ID` (числовой ID синтетического tenant) и `OPENAI_API_KEY` (ключ провайдера attacker/grader). Токен должен принадлежать тестовой учётной записи, а pharmacy ID должен относиться только к синтетическим данным.

```bash
npx promptfoo@latest redteam init --no-gui
npx promptfoo@latest redteam run
npx promptfoo@latest redteam report
```

Проверяйте сгенерированные атаки до выполнения. Target URL, bearer token и pharmacy ID задаются через окружение; провайдер attacker/grader явно указан как `openai:gpt-5`. Храните credentials в CI secret store или локальном окружении, никогда — в YAML или закоммиченных файлах. Не указывайте production URL. Red-team сканирование может создавать вредоносные prompts, поэтому ограничивайте доступ к артефактам и не используйте реальные данные пациентов.

## Release gates

1. Детерминированный CI должен пройти до рассмотрения любых model-based оценок.
2. Нарушения изоляции пациента/аптеки, ошибки дозировки/формы, потеря отрицания и неподтверждённые high-risk claims являются безусловными блокерами.
3. Результаты Ragas/DeepEval/HHEM сравниваются с версионируемой baseline; фиксируются judge model, revision, prompts, corpus/index revision и версия датасета.
4. Critical/high находки Promptfoo должны быть устранены или явно приняты как риск до релиза.
5. Включение в Production требует отдельно проверенного runtime decision gate, staged integration tests, бюджета latency/cost, fallback-поведения и плана rollback.
