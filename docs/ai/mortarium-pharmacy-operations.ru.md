# Операционная работа Mortarium в аптеке

## Архитектурное решение

Mortarium остаётся единым AI-ассистентом для фармацевта на базе существующих LangGraph PharmacistAgent и Agent Harness. Возможности аптеки предоставляются в виде ограниченных процессов и зарегистрированных MCP-инструментов, а не отдельных чат-ботов или независимых агентов.

LLM может интерпретировать запрос, объяснять утверждённую аптечную процедуру и запрашивать доступные только для чтения операционные данные. ERP-сервисы Pharmaviyum остаются единственным источником достоверного состояния бизнеса и детерминированных правил.

## Текущие операционные инструменты только для чтения

Следующие инструменты зарегистрированы в едином MCP-сервере Pharmaviyum:

| Инструмент | Домен | Контракт |
|---|---|---|
| `search_pharmacy_products` | Лекарства / каталог товаров для продажи | Поиск активных аптечных товаров по названию, INN, SKU, штрихкоду, производителю, дозировке или форме; возвращает доступный остаток |
| `get_inventory_overview` | Запасы | Чтение остатков по партиям: фактическое количество, резерв, доступное количество и порог пополнения |
| `get_expiring_inventory` | Партии / сроки годности | Поиск просроченных или скоро истекающих партий; фактический и зарезервированный остатки показываются отдельно от доступного для продажи количества |
| `get_sales_summary` | POS / продажи | Чтение завершённой выручки и количества транзакций за включительный диапазон дат |
| `get_pharmacy_workflow_guide` | Аптечные процессы | Объяснение базовых шагов и критических контролей для продажи, приёмки, инвентаризации, перемещений, возвратов, отзыва, закупок, кассовых смен и отпуска по рецепту |

Все пять инструментов доступны только для чтения. Идентификаторы аптеки и пользователя берутся из доверенного MCP-контекста авторизации запроса, а не из аргументов инструмента, переданных LLM. Поиск товаров применяет существующие исключения каталога продаваемых товаров. Запросы по запасам и продажам фильтруются по аутентифицированной аптеке. Просроченные партии остаются видимыми для сверки, но их `available_quantity` всегда равен нулю; `on_hand_quantity` и `reserved_quantity` отдельно отражают физическое и зарезервированное количество. Сравнение сроков годности использует UTC в соответствии с соглашением о временных метках запасов.

Схемы инструментов ограничивают длину запроса, число результатов и диапазоны дат. Эти инструменты не создают заказы, не принимают товар, не завершают продажи, не оформляют возвраты, не списывают запасы и не меняют цены товаров.

## Помощь в процессе и выполнение процесса — разные вещи

Mortarium поддерживает два разных сценария:

1. **Помощь знаниями:** объяснение процесса на основе утверждённых доказательств с учётом применимой юрисдикции. Если релевантные доказательства не найдены, ассистент должен сообщить, что процедуру не удалось проверить.
2. **Операционная помощь:** вызов разрешённого read-only MCP-инструмента для проверки актуальных данных ERP и суммирование результата с указанием его происхождения.

Операции записи остаются в детерминированных ERP endpoints и пользовательских интерфейсах. Будущий инструмент с возможностью записи должен иметь узкую типизированную схему, tenant-контекст, полученный на сервере, проверки роли/разрешений, идемпотентность там, где она применима, аудит и явное подтверждение человеком. LLM не должна напрямую записывать данные в БД или делать вывод, что транзакция завершилась успешно.

## Операции, пока не предоставленные Mortarium как инструменты

Перед добавлением инструментов записи или транзакций для создания заказов поставщикам, приёмки поставок, межфилиальных перемещений, инвентаризации, возвратов/возмещений, отзыва/карантина, управления кассовыми сменами или финансовых проводок необходимо проверить текущие доменные модели и API. Описание процесса в документации не доказывает наличие соответствующего исполняемого API.

В домене закупок сейчас есть записи поставщиков, но в проверенной поверхности моделей/API не обнаружен полный жизненный цикл заказа на закупку. Mortarium не должен выдумывать статус закупки или создавать заказ до реализации авторитетного процесса.

## Безопасность

- Идентификатор tenant и роль берутся из аутентифицированных API dependencies и request-scoped MCP context.
- Инструменты регистрируются с метаданными роли и класса выполнения.
- LLM видит только инструменты, доступные аутентифицированной роли.
- Не предоставляются неограниченные инструменты SQL, shell, файловой системы или произвольного исполнения кода.
- Количество запасов, допустимость срока годности, FEFO, цены, состояние оплаты, требования к рецепту и авторизация определяются правилами ERP.
- Информация о конкретном пациенте подчиняется авторизации в области пациента. MCP `get_patient_history` теперь связан с trusted selected patient и одной controlled purpose, требует роль pharmacist, повторно проверяет pharmacy ownership и записывает metadata-only allowed/denied `PHIAccessAudit` до возврата данных. Ответ всё ещё шире minimum-necessary target; database-backed audit tests и staged verification остаются открытыми. HMAC session isolation не заменяет tool-level authorization.
- Память диалога и thread checkpoint LangGraph в коде привязаны к pharmacy, authenticated user, patient (включая явную область без пациента) и client session через версионированные HMAC namespaces. Реализация объединена через PR #287 и имеет regression coverage. Staged end-to-end validation с PostgreSQL checkpoints и Redis memory остаётся release gate; merge/CI не доказывают production activation. См. [изоляцию состояния диалога по пациенту](patient-session-isolation.md) и [аудит архитектуры Mortarium](../rag_architecture_audit.md).
- Результаты инструментов и извлечённые документы являются недоверенными данными, а не инструкциями.
- Данные пациентов не добавляются в evaluation fixtures или prompts внешних judge-моделей.

## Проверка

Запустите детерминированные тесты регистрации инструментов и контрактов схем:

```bash
uv run pytest tests/unit/ai/test_pharmacy_operations_mcp.py -v
```

Следующий уровень интеграционных тестов должен запускать инструменты на тестовой БД с фиктивными записями других аптек и проверять, что ни один результат не пересекает границы tenant. Не считайте одни только schema tests доказательством production-изоляции.
