# Архитектура Mortarium AI и глоссарий

**Назначение:** определить роль, границы и терминологию AI-слоя Pharmaviyum. Документ отделяет текущее поведение репозитория от целевых возможностей: само наличие термина не доказывает, что функция развернута или проверена в production.

## 1. Официальное определение

**Mortarium AI — это защищённый, учитывающий контекст агентный фармацевтический интеллектуальный слой, интегрированный в Pharmaviyum ERP/CRM.** Он объединяет рассуждения языковых моделей, оркестрацию LangGraph, генерацию с дополненной поиском (RAG), обработку фармацевтических документов, изолированную память и контролируемые интеграции инструментов, чтобы предоставлять фармацевтическим специалистам прослеживаемую помощь, основанную на подтверждающих данных. Архитектура предусматривает авторизацию с учётом аптеки и пациента, оценку качества и наблюдаемость.

Mortarium — подсистема поддержки принятия решений, а не система учёта (system of record), клинический авторитет, автономный назначающий специалист, механизм разрешения отпуска или замена квалифицированного фармацевта. Детерминированные сервисы приложения остаются авторитетными для идентификации, разрешений, расчётов, запасов, транзакций и регулируемых процессов.

## 2. Концептуальная архитектура

```text
Pharmaviyum ERP/CRM (React UI, FastAPI API)
                    |
          Аутентификация и авторизация
                    |
       Mortarium AI Harness / Agent Runtime
       |            |                 |
   LangGraph      Память          Защитные механизмы
       |        (с областью          (Guardrails)
       |         действия)
       +------------+-----------------+
                    |
       +------------+-------------+
       |                          |
   LangGraph RAG              AI-агенты
       |                          |
 Преобразование запроса       MCP / API-инструменты
 Поиск + фильтры                  |
 Гибридный поиск             Авторизованные сервисы
       |
 PostgreSQL + pgvector
       |
 Ответ LLM, основанный на доказательствах
       |
 Проверка ссылок и результата
       |
 Проверка фармацевтом

Вспомогательные возможности:
Celery ingestion | Redis | оценка Ragas | OpenTelemetry
```

Это логическое представление компонентов. Оно не означает, что каждый блок является отдельным сервисом или что все целевые интеграции активны в production.

## 3. Основные понятия

### AI-слой
Архитектурный слой приложения, объединяющий модели, поиск, агентов, инструменты, память, средства безопасности, оценку качества и телеметрию. В Pharmaviyum эту роль выполняет Mortarium.

### LLM — Large Language Model (большая языковая модель)
Модель, обученная понимать и генерировать естественный язык. Она интерпретирует вопросы фармацевта и формирует черновики ответов. LLM может выдавать правдоподобные, но неподтверждённые утверждения; поэтому ответы должны опираться на доверенные источники и ограничиваться детерминированными правилами приложения.

### Конфигурация моделей: Demo, локальная разработка и Production
Репозиторий разделяет модель чата/генерации и модель эмбеддингов. Провайдер и модель выбираются настройками окружения. Значения ниже описывают конфигурационные значения по умолчанию в коде и документированный профиль FastAPI Cloud Demo, а не доказывают, какая модель активна в работающем deployment.

| Профиль | Провайдер / модель чата | Провайдер / модель эмбеддингов | Статус и ограничения |
|---|---|---|---|
| Локальная разработка по умолчанию | Ollama / `qwen3.5:9b` для быстрых, основных и сложных задач | Ollama / `mxbai-embed-large` (1024 измерения) | Значения кода при `USE_CLOUD_LLM=false`; необходим доступный сервис Ollama и загруженные модели |
| FastAPI Cloud Demo | QwenCloud / `qwen3.8-flash` для основных, быстрых и сложных задач | Отдельные OpenAI embeddings / `text-embedding-3-small` (1024 измерения), если настроены | Профиль описан в runbook развертывания; обязательны ограничение только бесплатной квотой и настройка в консоли провайдера. QwenCloud chat generation сам по себе не предоставляет модель эмбеддингов |
| Production | В конфигурации репозитория не определена отдельная production-модель | Должна быть отдельно настроена и проверена | Текущий runbook FastAPI Cloud повторяет Demo-профиль QwenCloud. Это не является утверждённым SLA production и не доказывает фактическую конфигурацию runtime. Перед релизом необходимо проверить production-модель по защищённой конфигурации runtime и телеметрии провайдера |

В коде также присутствуют необязательные настройки провайдеров Gemini и Groq. Их наличие в конфигурации не означает, что они активны. Не определяйте фактическую модель только по значениям по умолчанию: проверяйте эффективные `USE_CLOUD_LLM`, `CLOUD_LLM_PROVIDER`, переменные модели конкретного провайдера и учётные данные embeddings в deployment-окружении, не раскрывая секреты. Для production-профиля должны быть явно утверждены провайдер, модель/версия, политика квот и оплаты, разрешение на обработку данных, тайм-ауты/повторы и поведение при отказе. Не переключайтесь незаметно на платного провайдера.

### RAG — Retrieval-Augmented Generation
Подход, при котором система сначала извлекает релевантные внешние знания, а затем передаёт их LLM для генерации ответа. В Mortarium предполагаемая последовательность такова: подготовка запроса → поиск с учётом области доступа → оценка/отбор доказательств → сборка контекста → генерация → проверка результата и цитат. RAG снижает зависимость от знаний, усвоенных моделью при обучении, но не гарантирует правильность ответа.

### LangGraph
Фреймворк для определения stateful-процессов и агентов на основе графов. Узлы выполняют шаги, рёбра управляют переходами, условные рёбра выбирают ветви, а state переносит данные процесса. Checkpointing позволяет сохранять состояние графа. Mortarium использует LangGraph для оркестрации агента фармацевта и RAG-процесса. LangGraph — это не LLM, не векторная база данных и не система авторизации.

### AI Harness / Agent Harness
Слой управления выполнением вокруг вызовов моделей и агентов. В Mortarium он отвечает за сквозные входные/выходные проверки, ограниченную память и оркестрацию кеша, маршрутизацию моделей, лимиты выполнения, структурирование ответа и телеметрию. Harness задаёт ограничения выполнения, а LangGraph определяет граф процесса. Эти компоненты дополняют друг друга.

### MCP — Model Context Protocol
Протокол для предоставления AI-приложениям инструментов и ресурсов через стандартизированный интерфейс. Mortarium может использовать MCP для подключения агентов к разрешённым возможностям Pharmaviyum и внешним источникам информации. MCP стандартизирует обмен данными, но не выдаёт разрешения. Сервер обязан аутентифицировать вызывающую сторону, авторизовать каждую операцию, проверять аргументы и минимизировать возвращаемые данные.

### AI-агент
Процесс под управлением модели, который может выбирать между явно разрешёнными шагами и инструментами для выполнения задачи. В аптечном процессе агент может искать сведения о товаре или суммировать разрешённые записи. Модель может предложить вызов инструмента, но решение о разрешении принимает детерминированная серверная политика. Намерение модели никогда не является подтверждением записи или клинического действия.

## 4. Поиск и данные

### Embeddings (эмбеддинги)
Числовые векторы, представляющие текст или другой контент в пространстве эмбеддингов модели. Близкие по смыслу фрагменты могут иметь близкие векторы. Модель эмбеддингов создаёт векторы, а pgvector хранит их и выполняет поиск.

### Vector store (векторное хранилище)
Хранилище, сохраняющее эмбеддинги и поддерживающее поиск ближайших соседей по сходству. Документированная архитектура Mortarium использует PostgreSQL с pgvector.

### PostgreSQL
PostgreSQL — основная реляционная система управления базами данных (RDBMS) Pharmaviyum. Она хранит долговременные структурированные данные приложения и предоставляет транзакции, ограничения, индексы, SQL-запросы и миграции. Это system of record для бизнес-сущностей и транзакционного состояния; текст, созданный AI, не должен становиться авторитетным состоянием БД без проверенных прикладных процессов.

В Mortarium PostgreSQL также хранит записи RAG-чанков и обеспечивает долговременное хранение checkpoint-состояния LangGraph. Production-подключения передаются через защищённые настройки `DATABASE_URL` / `PGVECTOR_DATABASE_URL`; учётные данные нельзя помещать в документацию или логи.

### pgvector
Расширение PostgreSQL, добавляющее тип vector, операторы и индексы поиска по сходству, включая HNSW и IVFFlat. Оно позволяет выполнять векторный поиск вместе с реляционными запросами и SQL-фильтрами. pgvector не создаёт эмбеддинги и самостоятельно не обеспечивает прикладную авторизацию. PostgreSQL остаётся базой данных; pgvector — расширение, а не отдельная БД.

### Chunking (чанкинг)
Разделение исходного документа на ограниченные по размеру единицы поиска с сохранением смысла, структуры, происхождения и метаданных. Фармацевтический чанкинг должен сохранять связь названия препарата, дозировки/силы, единиц измерения, лекарственной формы, пути введения, условий, предупреждений и отрицаний с соответствующим текстом.

**Граница текущей реализации:** `MedicalChunker` в репозитории предоставляет три стратегии: `medical`, `semantic` и `recursive`. Режим medical распознаёт ограниченный набор заголовков разделов (показания, дозировка, противопоказания, взаимодействия и побочные эффекты), затем делит слишком большие разделы. Режим semantic группирует фрагменты, похожие на предложения, в пределах заданного бюджета; это не семантическое разбиение на основе embeddings. Режим recursive использует резервную последовательность разделителей: абзацы/переводы строк/предложения/пробелы. Значения по умолчанию — 512 оценочных токенов и 50 единиц перекрытия. Оценка использует `len(text) // 4`, а не токенизатор embedding-модели. Celery ingestion task по умолчанию использует `medical`, если не переопределён `chunking_strategy`. Нельзя описывать как реализованные table-aware parsing, точный токенизатор, полноценный двуязычный разбор разделов, parent-child retrieval или якоря страниц, пока они отдельно не реализованы и не покрыты тестами. См. [pipeline чанкинга](./chunking-pipeline.ru.md).

### Metadata (метаданные)
Структурированные атрибуты документов/чанков: источник, тип документа, язык, юрисдикция, область аптеки, уровень доступа и область пациента. Метаданные поддерживают фильтрацию, происхождение данных и управление жизненным циклом; они должны формироваться из доверенного контекста ingestion, а не выдумываться моделью.

### Область аптеки и пациента
Идентификатор аптеки является границей tenant. Для доказательств уровня пациента дополнительно требуется точный авторизованный идентификатор пациента. Чанки публичного уровня и уровня аптеки не должны содержать идентификатор пациента. Если пациент не выбран, patient-level чанки должны исключаться, а не совпадать по wildcard. Все этапы retrieval, расширение parent/source, память, кеши и checkpoint должны сохранять одну и ту же область доступа и работать по принципу fail closed.

### Hybrid search (гибридный поиск)
Стратегия поиска, объединяющая лексический/ключевой поиск (для точных названий препаратов, дозировок, кодов и фраз) с векторным поиском по сходству (для семантических совпадений). Два набора результатов могут объединяться и повторно ранжироваться. Для точных фармацевтических идентификаторов нельзя полагаться только на семантическое сходство.

### Reranker (модуль повторного ранжирования)
Модель или компонент оценки, который меняет порядок первоначальных кандидатов поиска по их релевантности запросу. Это необязательный второй этап retrieval. Не утверждайте, что он активен в runtime, пока конкретная реализация не подключена, не настроена и не протестирована.

### Context engineering (проектирование контекста)
Выбор, структурирование и ограничение объёма информации, передаваемой модели: запрос пользователя, доверенный контекст приложения, извлечённые доказательства, состояние диалога, инструкции и доступные инструменты. Это включает prompt engineering, но понятие шире.

### Citation and provenance (цитирование и происхождение данных)
Цитата связывает утверждение ответа со стабильным источником и, если доступно, с конкретной версией документа, разделом или страницей. Одного идентификатора источника недостаточно: процитированный материал действительно должен подтверждать утверждение.

## 5. Runtime, интеграции и фоновые задачи

### Redis
In-memory платформа данных, обычно используемая для ограниченных кешей, временного состояния, очередей и координации. В Mortarium она может поддерживать изолированную память диалога и кеширование. Redis не является авторитетной записью о пациенте. Ключи кеша и памяти должны включать все измерения области доступа и не допускать утечки данных пациента между пользователями или пациентами.

### Celery
Распределённая очередь задач для асинхронной фоновой работы. Ingestion-процесс Mortarium использует фоновые задачи для обработки документов, чанкинга, создания embeddings и сохранения результатов. Задачи должны быть идемпотентными, ограниченными, наблюдаемыми и безопасными для повторного запуска. Ingestion данных пациента заблокирован, пока отдельный авторизованный процесс не проверяет принадлежность пациента и применимые требования согласия/хранения.

### API-инструменты
Детерминированные сервисы приложения, доступные агентам через контролируемые интерфейсы. Операции чтения возвращают минимально необходимый авторизованный набор данных. Запись требует явной серверной авторизации и отдельного процесса подтверждения; модель не может сама разрешать свои действия.

## 6. Оценка качества, безопасность и наблюдаемость

### Ragas
Фреймворк для оценки RAG-процессов с помощью метрик faithfulness, answer relevancy, context precision и context recall. В этом проекте он предназначен для offline-оценки, а не как зависимость production request path. Его оценки — сигналы регрессии, а не клиническая валидация или регуляторная сертификация.

### Фармацевтическая оценка
Общие RAG-метрики необходимо дополнять предметными проверками:
- корректность цитат на уровне утверждений;
- точность названия препарата, действующего вещества, дозировки/силы, единиц, лекарственной формы и пути введения;
- сохранение отрицаний и условных формулировок;
- доля неподтверждённых клинических утверждений;
- изоляция контекста аптеки/пациента;
- качество поиска на английском и русском языках;
- безопасный отказ от ответа при отсутствии, устаревании или конфликте доказательств.

Используйте синтетические или деидентифицированные данные; клинические пороги должны проходить квалифицированную проверку.

### Guardrails (защитные механизмы)
Детерминированные и модельно-ассистированные средства контроля, ограничивающие входные данные, использование инструментов и выходные результаты. Они включают проверки авторизации, валидацию схем, защиту от prompt injection, правила отказа/воздержания от ответа, проверку результата и бюджеты выполнения. Guardrails дополняют, но не заменяют серверную авторизацию.

### Изоляция контекста пациента
Свойство безопасности, при котором данные, память, результаты поиска, кеши и checkpoint одного пациента не могут попасть в контекст другого пациента. Оно должно обеспечиваться на каждом этапе, а не только в финальном prompt. Код репозитория включает проверку области пациента и HMAC-namespace для сессий/checkpoint; интеграционные тесты PostgreSQL/Redis и production-проверка остаются отдельными release gates.

### OpenTelemetry
Независимый от поставщика стандарт, набор API и SDK для сбора traces, metrics и logs. Он помогает диагностировать задержки, ошибки и поведение процессов на уровнях API, графа, retrieval и фоновых задач. Телеметрия не должна содержать идентификаторы пациентов, содержимое рецептов, prompts, completions или извлечённый клинический текст, если отдельная утверждённая схема защиты данных явно этого не разрешает.

## 7. Карта ответственности компонентов

| Область | Основные компоненты | Ответственность |
|---|---|---|
| Понимание и генерация языка | LLM | Интерпретация запросов и подготовка ответов в границах доказательств |
| Оркестрация процессов | LangGraph | Управление состоянием графа и путями выполнения |
| Сквозные runtime-контроли | AI Harness | Лимиты выполнения, политика памяти/кеша и guardrails |
| Поиск знаний | RAG | Извлечение доказательств до генерации |
| Векторное сходство | Embeddings + pgvector | Представление и поиск семантически похожего содержимого |
| Поиск точных терминов | Лексический поиск PostgreSQL | Поиск точных названий, кодов, дозировок и фраз |
| Внешние возможности | MCP / API-инструменты | Предоставление разрешённых инструментов и ресурсов |
| Фоновый ingestion | Celery | Асинхронная обработка и индексация документов |
| Временное состояние | Redis | Изолированная память, кеш и координация |
| Измерение качества | Ragas + детерминированные тесты | Оценка регрессий поиска и ответов |
| Диагностика | OpenTelemetry | Трассировка и измерение поведения системы |

## 8. Обязательные инженерные принципы

1. Детерминированный код приложения отвечает за аутентификацию, авторизацию, расчёты и операции записи.
2. Никогда не доверяйте идентификаторам пациента, аптеки, пользователя или роли, переданным LLM.
3. Применяйте фильтры аптеки и пациента до retrieval и повторно при расширении parent/source.
4. При отсутствии, некорректности или неоднозначности области доступа завершайте операцию безопасным отказом; никогда не повторяйте запрос без scope.
5. Сохраняйте provenance источника, версию, язык, юрисдикцию, единицы дозировки и отрицания.
6. Считайте извлечённые документы и результаты инструментов недоверенными входными данными.
7. Не записывайте в логи идентификаторы пациентов, данные рецептов, prompts, completions или извлечённый клинический текст.
8. Не описывайте целевую возможность как реализованную, пока это не подтверждено кодом, тестами и эксплуатационными данными.
9. Фармацевт сохраняет ответственность за профессиональные решения.
