# Pipeline чанкинга Mortarium для фармацевтических документов

[English](chunking-pipeline.md) · **Русский**

**Статус:** архитектурная документация текущей реализации и поэтапной целевой архитектуры. Документ отделяет уже реализованное поведение от возможностей, для которых ещё требуются реализация и тесты.

## 1. Назначение и свойства безопасности

Chunking (разбиение на чанки) преобразует исходные документы в ограниченные по размеру единицы доказательств для LangGraph RAG workflow Mortarium. В аптечной системе чанк должен сохранять клинический смысл и контекст интерпретации: идентификатор препарата, дозировку, лекарственную форму, путь введения, популяцию, условия, предупреждения, отрицания, юрисдикцию, источник и версию.

Чанк — это единица индексации, а не самостоятельный клинический авторитет. Авторитетным остаётся исходный документ. Retrieval и generation должны учитывать tenant и пациента, опираться на доказательства и сохранять ссылки на источники.

## 2. Текущая реализация в репозитории

Текущая реализация находится в `src/pharmaviyum/ai/mortarium_rag/chunking.py`:

- `MedicalChunker` предоставляет стратегии `medical`, `semantic` и `recursive`.
- Стратегия medical обнаруживает ограниченный набор заголовков (показания, дозировка, противопоказания, взаимодействия и побочные эффекты) и разделяет текст секций.
- Стратегия semantic группирует фрагменты, похожие на предложения, в пределах заданного token budget.
- Стратегия recursive последовательно использует разделители абзацев, переводов строк, предложений и пробелов.
- Значения по умолчанию: 512 оценочных токенов и 50 единиц overlap.
- Чанки сохраняют document ID, последовательный chunk index, тип чанка, число токенов и скопированные метаданные документа (включая source, document type, country и language).
- Совместимый метод `RAGPipeline.ingest` вызывает chunker, создаёт embeddings содержимого и выполняет upsert чанков в vector store.

**Важные ограничения текущей реализации:**

1. Текущий счётчик токенов — `len(text) // 4`: это приблизительная эвристика по символам, а не tokenizer embedding-модели. Token budget является оценочным.
2. Текущая стратегия `semantic` группирует предложения; это не поиск семантических границ на основе embeddings.
3. Обнаружение заголовков эвристическое и пока поддерживает ограниченный набор языков. Нельзя заявлять о полном разборе секций SmPC на русском и английском.
4. Текущая схема Chunk не задаёт полноценную связь parent/child, диапазоны страниц/символов, структуру таблиц, путь заголовков или версию chunking/index.
5. Специализированного parser для таблиц нет. В зависимости от loader таблицы могут быть уплощены или разделены общими разделителями.
6. Гибкие metadata в текущем Chunk не доказывают, что расположение каждого источника или каждая лекарственная сущность извлечены правильно.
7. Документированный активный API ingestion path использует Celery. API task path и compatibility facade нужно проверять отдельно; нельзя предполагать одинаковую авторизацию, идемпотентность и обработку metadata.

Это известные ограничения кода, но не доказательство того, что каждый запуск ingestion ошибочен.

## 3. Целевой pipeline

Рекомендуемая целевая архитектура — версионируемый гибридный pipeline с учётом структуры документа:

```text
Исходный файл / источник
  -> loader с учётом формата и извлечение структуры
  -> нормализация (сохранить заголовки, таблицы, списки и page anchors)
  -> проверка идентичности документа, юрисдикции и версии
  -> сегментация по структуре разделов
  -> семантическое уточнение внутри секции (опционально, измеряемое)
  -> ограниченные child chunks + контекст родительской секции
  -> обогащение metadata и сущностями
  -> embeddings и лексическая индексация
  -> публикация версионируемого индекса
  -> tenant-scoped hybrid retrieval и reranking
  -> LangGraph grading, сжатие доказательств и генерация с citations
```

### Ответственность стратегий

| Стратегия | Назначение | Ограничение |
|---|---|---|
| Structure-aware | Разделение по границам документа/секции/подсекции | Нельзя отделять содержимое секции от пути её заголовков |
| Semantic refinement | Улучшение границ внутри длинных секций | Сохранять предложения и клинические положения целиком |
| Parent-child | Искать точные child-доказательства и возвращать ограниченный parent-контекст | Parent и child должны иметь одинаковые document, version и access scope |
| Table-aware | Сохранять отношения строк, столбцов и заголовков | Нельзя превращать дозу/значение в число без подписи |
| Recursive fallback | Ограничивать размер неструктурированного или повреждённого текста | Отмечать использование fallback в metadata и telemetry качества |
| Multilingual | Поддерживать языковой разбор и поиск | Сохранять оригинальный текст; не переводить доказательства незаметно |

Обычный recursive splitter остаётся безопасным резервным механизмом, но не предпочтительной основной стратегией для структурированной информации о лекарствах.

## 4. Контракт содержимого чанка и metadata

Каждый чанк должен сохранять исходный текст доказательства и, если данные доступны, включать:

- **Идентичность:** `document_id`, `chunk_id`, `chunk_index`, `parent_chunk_id`.
- **Происхождение:** source URI или стабильный source key, тип документа, издатель, версия, content hash, даты публикации/действия, страница и source offsets.
- **Структура:** section ID, heading path, тип секции, table ID/row identifiers и тип чанка.
- **Область доступа:** pharmacy/tenant ID, access level, patient ID только для документов с областью конкретного пациента, юрисдикция/страна.
- **Язык:** определённый и объявленный язык с сохранением оригинала.
- **Фармацевтические сущности:** канонические drug/ingredient IDs, название препарата, дозировка, форма, путь введения и популяция — только если они надёжно извлечены и проверены.
- **Обработка:** стратегия/версия chunking, версия parser, tokenizer/model ID, оценочное или измеренное число токенов, fallback flags и ingestion/index revision.

Пример структуры (иллюстративный контракт, а не утверждение, что все поля уже сохраняются):

```json
{
  "document_id": "smPC_001",
  "chunk_id": "smPC_001_v3_child_014",
  "parent_chunk_id": "smPC_001_v3_section_04",
  "section": "Contraindications",
  "heading_path": ["4. Clinical particulars", "4.3 Contraindications"],
  "language": "en",
  "country": "GB",
  "drug_name": "Omeprazole",
  "active_ingredient": "omeprazole",
  "strength": "20 mg",
  "dosage_form": "capsule",
  "source_page": 4,
  "document_version": "3",
  "chunking_version": "medical-v2",
  "chunk_type": "contraindications"
}
```

Не выдумывайте отсутствующие metadata. Неизвестные значения остаются null/отсутствующими и не должны выводиться моделью во время ingestion.

## 5. Правила сохранения фармацевтического смысла

- Название препарата должно оставаться связанным с текстом, к которому оно относится.
- Дозировка, единицы, лекарственная форма и путь введения должны сохраняться вместе; нельзя отделять числовую дозу от единицы измерения или популяции.
- Сохраняйте отрицания, неопределённость, условные формулировки, исключения и временные уточнения (например, «не рекомендуется», «только если», «за исключением», «у пациентов с»).
- Противопоказания, предупреждения, взаимодействия, инструкции по дозированию и нежелательные реакции должны оставаться различимыми.
- Заголовки таблиц должны сохраняться с каждой строкой; объединённые ячейки и сноски следует явно представлять, если parser источника это поддерживает.
- Не объединяйте противоречивые утверждения из разных документов или версий в один чанк.
- Сохраняйте юрисдикцию, даты действия и версию источника для retrieval filters и citations.
- Сохраняйте исходный текст; нормализованное или переведённое представление должно иметь отдельную маркировку и ссылку на оригинал.

## 6. Начальный профиль настройки

Это экспериментальные стартовые диапазоны, а не клинические стандарты или фиксированные production defaults:

| Настройка | Начальный эксперимент |
|---|---:|
| Размер child chunk | 200–400 tokenizer tokens |
| Общий размер chunk | 400–700 tokenizer tokens |
| Контекст parent section | 1 000–1 500 tokenizer tokens, с ограничением |
| Overlap | 50–100 tokenizer tokens, только если это не дублирует и не искажает таблицу/список |
| Retrieval candidates | Настраивать по размеченному корпусу и бюджету latency |
| Tokenizer | По возможности использовать tokenizer embedding-модели |

Текущие значения 512/50 приблизительны, поскольку счётчик делит количество символов на четыре. Не сравнивайте их напрямую с измерениями настоящего tokenizer. Настраивайте параметры по типу документа, языку и секции; оценивайте качество retrieval вместе со стоимостью.

## 7. Версионирование, повторный ingestion и публикация

Рассматривайте исходные документы, конфигурацию chunking и embeddings как версионируемые артефакты.

- Вычисляйте стабильный content hash нормализованного источника и сохраняйте версии parser/chunker.
- Делайте ingestion идемпотентным для одной и той же версии источника и конфигурации обработки.
- Создавайте новую revision индекса параллельно с активной; не перезаписывайте единственный рабочий индекс на месте.
- До переключения активной revision проверяйте количество чанков, provenance, полноту metadata и retrieval-регрессии.
- Сохраняйте предыдущую revision для rollback согласно утверждённой политике хранения.
- Изменение chunker, parser, embedding-модели или критического mapping metadata требует переиндексации и benchmark evidence.
- Не смешивайте чанки несовместимых версий документов без явной обработки актуальности и юрисдикции.

## 8. Интеграция с retrieval и LangGraph

Chunking предшествует существующему LangGraph RAG graph. Сам graph отвечает за преобразование запроса, retrieval с учётом области доступа, оценку документов, ограниченное переписывание запроса, сжатие доказательств, генерацию и guardrails результата.

Retrieval должен применять аутентифицированную область аптеки и, для данных пациента, явную область конкретного пациента. При расширении parent необходимо повторно применить те же фильтры авторизации: нельзя безопасно получить child, а затем загрузить неразрешённый parent.

Citations должны вести к исходному документу и его точной версии/странице/секции, если эти данные доступны. Compression обязана сохранять source IDs и не удалять отрицания, единицы, условия и предупреждения. Query rewrite или HyDE — это помощь поиску, а не доказательство.

## 9. Оценка и критерии приёмки

Используйте offline-оценку Ragas вместе с детерминированными фармацевтическими regression-тестами. Сравнивайте версии chunking на одном и том же зафиксированном синтетическом или обезличенном корпусе и наборе запросов.

| Измерение качества | Что измерять |
|---|---|
| Context precision / recall | Находятся ли релевантные доказательства и не пропущены ли необходимые источники |
| Faithfulness | Подтверждаются ли утверждения ответа найденными доказательствами |
| Citation correctness | Entailment claim-to-source и точное разрешение источника/версии |
| Medication entity accuracy | Сохранение препарата, вещества, дозировки, единиц, формы и пути введения |
| Negation preservation | Сохранение полярности и условий при parsing, chunking, retrieval и compression |
| Table integrity | Сохранение связей заголовок/значение/строка |
| Multilingual retrieval | Recall и качество ответа отдельно для английского и русского (и каждого дополнительного языка) |
| Patient/pharmacy isolation | Отсутствие утечек между tenant/patient в evidence, parent expansion, cache и checkpoint |
| Freshness | Выбор корректной версии документа и юрисдикции |
| Operational cost | Время ingestion, объём embeddings, размер индекса, latency retrieval и частота ошибок |

Кандидат релиза должен пройти детерминированные проверки целостности и изоляции до рассмотрения агрегированных оценок Ragas. Пороговые значения устанавливаются по проверенной baseline; универсальные пороги не выдумываются. LLM-оценки — регрессионные сигналы, а не клиническая валидация, регуляторное одобрение или доказательство клинической безопасности.

## 10. Обязательные тестовые сценарии

Поддерживайте regression fixtures как минимум для следующих случаев:

1. Секция противопоказаний, заголовок которой должен оставаться связанным с содержимым.
2. Таблица дозировок с заголовками, несколькими дозировками, единицами и сносками.
3. Отрицательное утверждение и условное исключение.
4. Длинная секция, требующая нескольких child chunks и parent expansion.
5. Английская и русская версии эквивалентного исходного материала.
6. Две версии документа с разными датами вступления в силу.
7. Две аптеки и два пациента с совпадающими названиями препаратов.
8. Повреждённый текст, запускающий recursive fallback.
9. Повторный ingestion источника и retry после частичного сбоя.
10. Разрешение citation от child chunk к исходной странице и версии документа.

## 11. Безопасность и конфиденциальность

Metadata чанка является частью границы авторизации. Фильтры tenant и patient должны применяться доверенным серверным кодом, а не аргументами модели или пользовательскими metadata. Не помещайте PHI в chunk IDs, metric labels, trace attributes или обычные логи. Используйте синтетические/обезличенные fixtures для оценки. Политики хранения и удаления должны охватывать исходные файлы, чанки, embeddings, parent records, checkpoints и backups.

### 11A. Patient-scoped metadata и изоляция retrieval

Идентификатор пациента — это область авторизации, а не семантическая подсказка. Текущая RAG-схема уже определяет `pharmacy_id`, `access_level` (`public`, `pharmacy`, `patient`) и необязательный `patient_id`; `CanonicalMetadata` требует положительный `patient_id`, если `access_level="patient"`. `QueryContext` несёт аутентифицированную область аптеки и необязательный выбор пациента. Сохраняйте этот контракт как baseline совместимости; не добавляйте второе поле `tenant_id`, которое может расходиться с `pharmacy_id`, без отдельно проверенной миграции схемы.

**Контракт metadata:** используйте типизированную canonical ingestion model как источник истины, а в vector-store payload сериализуйте только поддерживаемые скалярные поля. Векторные хранилища часто ограничивают вложенные объекты и массивы, поэтому вложенный JSON-пример полезен для API/domain design, но не должен считаться напрямую индексируемым.

Пример канонической записи (заполнять только фактами, подтверждёнными источником или доверенным контекстом приложения):

```json
{
  "metadata_schema_version": "1",
  "document_id": "patient_record_001",
  "chunk_id": "patient_record_001_v1_014",
  "chunk_type": "patient_context",
  "pharmacy_id": 42,
  "access_level": "patient",
  "patient_id": 12345,
  "language": "en",
  "source": "record_001",
  "version": "record-revision-7",
  "category": "medication_history",
  "doc_type": "patient_record",
  "source_page": null,
  "section_code": "medication_history",
  "drug_name": "Omeprazole",
  "active_ingredient": "omeprazole",
  "strength": "20 mg",
  "dosage_form": "capsule",
  "route": "oral",
  "chunking_version": "medical-v2"
}
```

Пример иллюстративный, а не новая runtime-схема. В текущей реализации авторитетными являются поля `CanonicalMetadata`; фармацевтические enrichment-поля (например, `drug_name`, `strength`, page anchors и `chunking_version`) остаются необязательными, пока их извлечение, валидация и сохранение не реализованы. Не выдумывайте значения. Публичные SmPC/guideline chunks не должны содержать patient ID. Записи уровня аптеки используют `access_level="pharmacy"`. Записи пациента используют `access_level="patient"` и требуют одновременно разрешённую область аптеки и точную область пациента.

**Серверная политика retrieval (fail closed):**

1. Аутентифицируйте фармацевта и получайте `pharmacy_id` из доверенного состояния membership/authorization. Не принимайте область аптеки из prompt или аргументов инструмента, сгенерированных моделью.
2. Считайте `patient_id` в запросе только selector. До создания неизменяемого `QueryContext` проверьте, что пациент существует, активен (если применимо) и относится к аутентифицированной аптеке.
3. Формируйте retrieval filter в доверенном серверном коде. Всегда ограничивайте запрос разрешённым `pharmacy_id`; явно разрешайте только нужные access levels. Patient chunks включайте только при выбранном и проверенном пациенте, используя точное равенство `patient_id`. Если пациент не выбран, полностью исключайте patient-level records — никаких wildcard, null-as-anything или fallback без фильтра.
4. При ошибке проверки scope или построения filter возвращайте ошибку авторизации/валидации и не выполняйте более широкий поиск. Не повторяйте запрос молча без фильтров.
5. Применяйте одинаковые фильтры к vector, full-text/BM25, hybrid, reranker candidate fetches, parent expansion, citation/source lookup и любому вторичному retrieval path. При загрузке parent или source повторно проверяйте авторизацию: разрешённый child не разрешает доступ к parent.
6. Ограничивайте cache keys, Redis memory, LangGraph checkpoints и производные summaries по аутентифицированным pharmacy, user, patient (включая явное отсутствие пациента) и client session. Следуйте [ADR-0003](../adr/ADR-0003-patient-scoped-ai-state.md): одних retrieval filters недостаточно для изоляции состояния диалога.
7. Не раскрывайте реальные patient IDs в chunk IDs, prompts (где это можно избежать), logs, traces, metric labels или сообщениях об ошибках. Для внешних идентификаторов используйте opaque references, а для сохраняемого состояния — keyed HMAC namespaces согласно ADR-0003. Применяйте retention/deletion к исходным записям, чанкам, embeddings, cache, checkpoints и backups.

**Хранение и индексация:**

- Храните тело чанка в content field; metadata не заменяет исходный текст.
- Для фильтрации vector store используйте плоские metadata (например, `pharmacy_id`, `access_level`, `patient_id`, `country`, `language`, `doc_type`). Не сериализуйте произвольные вложенные объекты, если adapter явно не поддерживает и не тестирует их.
- Проверяйте инвариант `access_level == "patient" => patient_id is present` на границах ingestion и persistence, а не только в Pydantic request model.
- Рассматривайте public/pharmacy/patient как классы доступа, а не уровни достоверности. Публичный документ можно использовать глобально только если storage и authorization model явно поддерживают глобальную область; текущая схема всё ещё требует `pharmacy_id`.
- Если источник содержит нескольких пациентов, разделите его на отдельно авторизованные записи/чанки или исключите из patient-scoped индексации. Никогда не прикрепляйте несколько patient IDs к одному поисковому чанку.

**Обязательные тесты изоляции:** используйте синтетические fixtures минимум для двух аптек и двух пациентов. Проверьте, что:

- Пациент A не может получить чанк пациента B даже при одинаковом тексте запроса, названиях лекарств и score.
- Пациент A не может получить содержимое пациента B через vector, lexical, hybrid, reranked, parent-expansion, citation или source-fetch paths.
- Запрос без выбранного пациента не может получить ни один patient-level chunk.
- Поддельный, неизвестный или относящийся к другой аптеке patient selector отклоняется до retrieval.
- Ошибка filter/storage приводит к fail-closed и никогда не запускает unscoped fallback.
- Cache, Redis memory, summaries и PostgreSQL checkpoints изолированы при последовательности Patient A → Patient B → явно без пациента с повторным использованием client session, в streaming и non-streaming режимах.
- Тесты проверяют и возвращённый контент, и отсутствие идентификаторов/provenance чужой области доступа; нельзя ограничиваться mock unit-тестами filter builder.

**Статус реализации:** схема и compatibility pipeline предоставляют поля pharmacy/patient scope и построение scoped filters; ADR-0003 описывает patient-aware namespaces состояния. Эта документация не доказывает, что каждый активный ingestion, LangGraph, vector-store, cache, parent-expansion или production path обеспечивает всю политику. Каждый путь нужно отдельно проверить и протестировать до закрытия isolation gate.
