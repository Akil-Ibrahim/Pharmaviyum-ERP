# ADR-0006: Неизменяемый журнал движений складских запасов

**Статус:** Proposed (предложение; не принято как завершённый контракт)  
**Дата:** 2026-11-16  
**Ответственные:** инженерная команда Pharmaviyum

## Контекст

Inventory является операционной моделью текущих остатков по аптеке и партии. POS checkout, подтверждение платежа, ошибка платежа, отмена продажи, приёмка товара и административный endpoint инвентаризации сейчас изменяют физический остаток и/или резерв в нескольких отдельных участках кода.

Текущая модель проверяет неотрицательные значения и условие reserved_quantity <= quantity; POS использует блокировки строк при распределении партий. Это защищает важные инварианты, но не создаёт полного неизменяемого объяснения происхождения остатка. По одному текущему балансу нельзя достоверно установить, кто, зачем и в рамках какой продажи или приёмки изменил запас, а также не привёл ли повтор запроса к дублированию эффекта.

SaleItemAllocation хранит распределение партий по продаже, а transactional outbox — события для интеграции. Ни одна из этих таблиц не является универсальным складским журналом: allocation не описывает приёмки, корректировки и жизненный цикл резервов; outbox предназначен для доставки интеграционных событий, а не для ведения авторитетной истории запасов.

## Решение

Ввести append-only журнал InventoryMovement, сохранив Inventory в качестве авторитетной и оптимизированной для запросов проекции текущих остатков. Не создавать вторую конкурирующую таблицу текущих складских балансов.

Каждая запись движения должна содержать как минимум:

- идентичность аптеки и партии: pharmacy_id, inventory_id, product_id;
- тип движения movement_type с ограниченным набором допустимых значений;
- quantity_delta для физического остатка и reserved_quantity_delta для резерва;
- значения до и после движения для обеих величин;
- идентификатор пользователя/оператора, если он известен, и явную классификацию системного актора для подтверждённых системных операций;
- причину, тип и идентификатор связанного документа (например, receipt, sale receipt, payment, adjustment);
- стабильный idempotency key в области конкретной аптеки и операции;
- correlation/event identifier и UTC-время создания.

Запись журнала и соответствующее изменение баланса Inventory ДОЛЖНЫ фиксироваться в одной транзакции PostgreSQL. Сервис записи должен блокировать строку партии, проверять оба результирующих значения, отклонять повторный idempotency key, применять дельты и добавлять запись движения. При rollback не должно сохраняться ни изменение баланса, ни запись журнала.

### Семантика движений

| Операция | Дельта физического остатка | Дельта резерва |
|---|---:|---:|
| Приёмка товара | +n | 0 |
| Продажа за наличные / успешное подтверждение оплаты | -n | 0 |
| Резерв при внешней оплате | 0 | +n |
| Неуспешная оплата / отмена ожидающей оплаты продажи | 0 | -n |
| Подтверждение внешней оплаты | -n | -n |
| Корректировка по результатам пересчёта | знаковая разница | 0 |
| Списание / утилизация просроченного товара | -n | 0 |
| Возврат, принятый обратно в пригодный к продаже запас | +n | 0 |

Резервирование не является списанием физического товара. Подтверждение зарезервированной продажи изменяет обе величины в одной записи движения. Возврат отражается только после проверки и явного решения о disposition; повреждённый или помещённый в карантин товар не должен увеличивать продаваемый Inventory.quantity.

### Неизменяемость и удаление

Прикладные роли не должны обновлять или удалять записи движений. Исправления оформляются компенсирующими движениями со ссылкой на исходную запись; история не переписывается. Неизменяемость должна дополнительно обеспечиваться правами БД/триггерами и контролем хранения/резервного копирования, а не только соглашениями ORM.

Складские партии, на которые ссылается журнал, нельзя удалять. В дальнейшем их следует закрывать или архивировать, сохраняя историю. Существующие проверки удаления остаются обязательными и должны быть усилены при внедрении журнала.

### Миграция и поэтапное внедрение

1. Добавить таблицу журнала и ограничения отдельной additive Alembic migration. Перед созданием миграции проверить и согласовать все Alembic heads; не угадывать родительскую ревизию.
2. Не выдумывать исторические движения на основе текущих остатков. Если достоверной истории приёмок/пересчётов нет, записать явно помеченное событие opening balance с указанием происхождения миграции и времени миграции либо считать старые остатки непроверенными до авторизованной физической сверки. Выбранный подход должен быть утверждён до rollout.
3. Ввести единый транзакционный сервис движений и тесты его ограничений и идемпотентности.
4. Перевести все пути изменения запасов: приёмку, cash checkout, внешний резерв, settlement, failure, cancellation, административные корректировки и последующие возвраты/списания/перемещения.
5. Убрать прямое административное изменение reserved_quantity; прямые изменения quantity заменить явным процессом корректировки с обязательной причиной до объявления журнала завершённым.
6. Выполнить контролируемую миграцию и сверку; проверить существующие данные и конкурентные сценарии до включения нового пути записи.

## Инварианты

- quantity >= 0
- reserved_quantity >= 0
- reserved_quantity <= quantity
- available_quantity = quantity - reserved_quantity
- после rollout каждое изменение физического остатка или резерва имеет ровно одну соответствующую запись журнала;
- идемпотентность движений ограничена аптекой, повтор запроса не создаёт второго эффекта;
- pharmacy_id движения соответствует аптеке связанной партии;
- изменение баланса и запись журнала атомарны;
- переходы состояния продажи/платежа и складские движения атомарны;
- в метаданные складского журнала не копируются персональные данные пациентов.

## Обязательная валидация

- upgrade/downgrade миграции и полный migration lifecycle на чистом PostgreSQL;
- тесты неизменяемости журнала;
- тесты идемпотентности приёмки, checkout, webhook, отмены и корректировки;
- конкурентные тесты приёмки, резервирования и checkout;
- reconciliation-инвариант: сверка суммы дельт журнала с балансами Inventory;
- tenant isolation и атрибуция актора;
- fault-injection: rollback не оставляет ни запись журнала, ни изменение баланса.

## Последствия

Журнал обеспечивает проверяемую историю изменения запасов и основу для сверки, расследования инцидентов и будущей синхронизации Edge. Он увеличивает объём записей, сложность миграции и требует направить каждую операцию изменения запасов через единый сервис. Журнал нельзя считать реализованным или готовым к production, пока не переведены все пути изменения остатков и не пройдена указанная валидация.
