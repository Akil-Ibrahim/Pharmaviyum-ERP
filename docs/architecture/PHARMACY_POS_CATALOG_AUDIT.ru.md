# Pharmacy POS 2.0 и лекарственный каталог — первоначальный аудит кода

**Ветка аудита:** feature/pharmacy-pos-2  
**Базовая версия:** main на коммите 3d436a1b2280cb1e6d88a6c0664a1acf9b2c6dc9  
**Область:** read-only проверка кода приложения и файлов миграций. Production database не использовалась и не изменялась.

## Краткое резюме

В Pharmaviyum уже есть значимая основа аптечной предметной области. Правильный подход — последовательное расширение, а не переписывание с нуля.

Существующие компоненты:
- DrugReference, DrugReferenceIngredient и MedicinalProduct.
- Локальные продаваемые Product, опционально связанные с MedicinalProduct.
- Модели Inventory и ProductBatch.
- Скрипты импорта RxNorm и EMA.
- Поиск локальных товаров и поиск по справочному каталогу.
- React POS с поиском локальных товаров и справочника, вводом штрихкода, черновой корзиной, управлением количеством, скидками и диалогом оплаты.

Критический функциональный пробел — сохранение завершённой продажи. POS намеренно не завершает продажу, поскольку backend не сохраняет атомарно строки продажи, оплату, чек и складские движения на уровне партий.

## Результаты аудита

### 1. Существующая модель каталога

Файлы: src/pharmaviyum/models/drug_catalog.py, src/pharmaviyum/schemas/drug_catalog.py, src/pharmaviyum/api/v1/drug_catalog.py.

Схема различает каноническую справочную запись препарата и лекарственный продукт; локальный Product может ссылаться на medicinal product. Это хорошая основа.

Пробелы:
- В проверенной модели нет отдельной сущности сопоставления с внешними источниками и происхождения данных (provenance).
- Связи ингредиентов сейчас представляют один DrugReference на medicinal product; импортёры RxNorm и EMA пропускают продукты с несколькими ингредиентами. Это ограничение сохраняется до корректной поддержки комбинационных препаратов.
- API каталога предоставляет только поиск; управляемого workflow ручного создания и проверки нет.
- Запись каталога — справочная информация, а не локально разрешённый к продаже товар, цена или складская запись. UI показывает это различие, и его нужно сохранить.

### 2. Существующие импортёры

Файлы: scripts/import_rxnorm_catalog.py, scripts/import_ema_catalog.py, tests/unit/catalog/test_rxnorm_import.py, tests/unit/catalog/test_ema_import.py.

Импортёры помещают исходные записи в staging-таблицу drug_catalog_source_records, а не напрямую в DrugReference или MedicinalProduct. Каждая запись содержит source ID, SHA-256 checksum точного скачанного архива/workbook как версию источника, время извлечения, URL, осторожное примечание о лицензии и нормализованный payload. Повторный запуск того же файла идемпотентен для пары source/version. Новые записи получают pending_review; staging не создаёт и не изменяет утверждённые сущности каталога, продаваемые товары, цены, партии, остатки или сроки годности. Записи с несколькими ингредиентами исключены до корректной поддержки моделью.

RxNorm не является полным международным каталогом. EMA Article 57 — европейские справочные данные, а не доказательство регистрации препарата в каждой стране. DrugBank нельзя включать для коммерческого использования без подтверждения лицензии и прав на API. OpenFDA — регуляторные данные США, а не доказательство глобальной регистрации.

### 3. POS и сохранение продажи

Файлы: frontend/shadcn-admin/src/features/pos/index.tsx, src/pharmaviyum/api/v1/orders.py, src/pharmaviyum/models/order.py.

POS поддерживает локальный поиск, поиск по справочнику, черновую корзину, изменение количества, скидки и подготовку оплаты. Frontend блокирует завершение и показывает уведомление, поскольку безопасная серверная транзакция пока отсутствует.

Текущий Order API не является POS checkout API:
- Order ориентирован на пациента и не имеет сохраняемых строк заказа.
- Завершение создаёт одну агрегированную PatientPurchase, а не детализированные продажи товара/партии.
- Сумма использует поле БД с плавающей точкой в текущей миграции.
- Нет FEFO-распределения партий и атомарного сохранения оплаты, чека и складских движений.

Не включайте подтверждение оплаты на frontend как обходное решение. Реализуйте отдельный sale/checkout domain с транзакционными строками, состоянием оплаты, чеком, распределением партий и аудируемыми складскими движениями.

### 4. Склад и партии

Файлы: src/pharmaviyum/models/inventory.py, src/pharmaviyum/models/product_batch.py, src/pharmaviyum/models/product.py.

`Inventory` является авторитетной моделью аптечного остатка и партии согласно ADR-0006: она содержит `pharmacy_id`, `product_id`, `lot_number`, `expires_at`, физический остаток и резерв, а также связана с append-only журналом `InventoryMovement`. `ProductBatch` — legacy-модель для обратной совместимости: в ней нет `pharmacy_id` и хранится отдельный `available_quantity`; на неё всё ещё ссылаются `PatientPurchase`, dashboard-запросы и seed-код. Её нельзя использовать как источник истины для аптечных остатков, FEFO allocation или Edge-to-Central inventory mapping. Удалять или автоматически переносить её данные в рамках этого изменения нельзя: сначала нужно инвентаризировать все оставшиеся read/write paths, определить миграцию исторических ссылок `PatientPurchase.batch_id` и доказать, что операционные сценарии больше не зависят от её полей количества. Новая работа со складом и интеграцией должна разрешать партии через `Inventory` и общий movement service.

Product содержит legacy aggregate stock и цену Float. Сохраняйте их в период совместимости; для новых денежных транзакций используйте Decimal, а аптечный/партионный складской учёт считайте авторитетным там, где он уже определён.

### 5. Авторизация API и tenant scope

Проверенный endpoint поиска каталога требует аутентифицированного активного пользователя. Endpoints создания/обновления/удаления товаров используют superuser dependency. Проверенные запросы каталога и товаров не применяют pharmacy tenant filter; это может быть допустимо для общего справочного каталога, но не должно переноситься на принадлежащие аптеке товары и остатки.

До добавления управления каталогом определите permissions для специалистов каталога и проверяйте pharmacy scope на сервере. Проверок только на UI недостаточно.

### 6. Безопасность миграций и deployment

Файлы: alembic/env.py и alembic/versions/*.

Окружение Alembic предпочитает DATABASE_URL FastAPI Cloud и удаляет неподдерживаемый asyncpg параметр channel_binding. В цепочке миграций есть исторические ветви и merge revision; revision ID отличаются от некоторых имён файлов. Изменения должны опираться на реальные revision IDs и проверенный граф, а не только на имена файлов.

Аудит не подключался к production database, не проверял alembic_version и не выполнял миграции. До изменения схемы:
1. Проверьте alembic heads и alembic history в воспроизводимом local/staging.
2. Сравните revision развёрнутой БД с графом репозитория.
3. Проверьте upgrade и rollback на disposable local PostgreSQL instance или изолированной non-production БД с целевой схемой.
4. Создайте и проверьте восстанавливаемую резервную копию до production rollout.
5. Не выполняйте destructive cleanup и не переписывайте историю применённых миграций в рамках POS-функции.

## Предлагаемая последовательность реализации

### A. Управление Drug Catalog

- Реализованы типизированные контракты создания/просмотра/review source records и хранение provenance.
- Импортёры RxNorm и EMA помещают записи в staging с source identity и file-checksum versioning.
- Импортированные записи остаются pending review; повторные source/version пары пропускаются.
- Объяснимые match suggestions ранжируют существующие references/products; проверка человеком обязательна.
- Review API связывает staged-запись с существующей canonical reference или medicinal product; автоматического создания сущностей каталога нет.
- Справочные записи отделены от локальных продаваемых товаров и склада.

GET /drug-catalog/sources/{record_id}/matches ранжирует существующие canonical references и medicinal products по нормализованным ингредиентам, бренду/названию, концентрации, форме, пути введения и стране. Кандидаты сопровождаются понятными причинами и являются только рекомендациями. Endpoint не меняет review status и не записывает каталог; он ограничен pending source records.

### B. Управление локальными аптечными товарами

- Создавайте/связывайте продаваемый Product только после локальной проверки каталога.
- Требуйте pharmacy context для аптечных цен и складских операций.
- Проверяйте уникальность SKU и barcode/GTIN в правильной области.
- Сохраняйте legacy fields при переводе новых денежных операций на Decimal.

### C. Транзакционный POS checkout

- Введите контракты sale, sale item, payment, receipt и stock movement.
- Распределяйте подходящие партии по FEFO с блокировкой строк или эквивалентным concurrency control.
- Отклоняйте просроченные, quarantined, отозванные и иным образом заблокированные остатки.
- Используйте idempotency keys, чтобы retry не создавал дубли продаж.
- Атомарно фиксируйте строки продажи, состояние оплаты, чек и складские движения.
- Добавьте void/return/refund как аудируемые обратные операции.

### D. Проверка

- Unit-тесты matching, duplicate detection и FEFO selection.
- API-тесты authorization, tenant isolation, import review и checkout invariants.
- Integration-тесты rollback при ошибке оплаты/склада и конкурентной продажи последней единицы.
- Playwright-покрытие cashier workflow только после появления backend-контракта.

## Явные исключения из этого audit commit

- Production database не изменялась.
- Нет автоматического создания утверждённых записей каталога, локальных продаваемых товаров или остатков из внешних импортов.
- RxNorm, EMA, OpenFDA и DrugBank не объявляются доказательством локальной регистрации препарата.
- Checkout не включается до реализации backend-транзакции и тестов.

## Очередь проверки исходных записей в Admin

Аутентифицированный frontend включает страницу Catalog Review, связанную с endpoints source records, доступными только superuser:

- Показывает до 200 pending_review записей с source identity, version, временем извлечения, URL, условиями лицензии и нормализованным payload.
- По запросу получает explainable match suggestions и показывает confidence и причины совпадения.
- Требует явного выбора кандидата перед approve или пометкой duplicate; при reject target не прикрепляется.
- Отправляет ровно одну match target согласно backend schema.
- Обрабатывает API errors и обновляет очередь после успешного решения.

UI role check — только удобство. Граница безопасности — backend CurrentSuperuser dependencies. Решения review не создают локальные продаваемые товары, цены, партии, остатки или движения и не устанавливают разрешение на продажу на местном рынке.

## Получение кандидатов matching и ограниченная загрузка данных

Match endpoint сначала выполняет лёгкий проход по reference IDs/INN names и строкам ingredient names, используя тот же fuzzy similarity threshold, что и matching service. Затем ORM-объекты, связанные ингредиенты и medicinal products загружаются только для 250 лучших reference IDs. После этого вычисляются explainable product-level scores и возвращаются 10 лучших рекомендаций.

Это предотвращает загрузку в память приложения графа связей всех DrugReference для каждого review-запроса. Лёгкое сканирование имён всё ещё пропорционально размеру каталога; fuzzy matching намеренно сохраняется вместо ограничительного exact/prefix-only SQL-фильтра. В будущем database-specific trigram/full-text index может снизить стоимость сканирования после проверки доступности extension и query plans на целевой БД.


## Повторный аудит: карта зависимостей legacy ProductBatch

**Базовая версия повторного аудита:** актуальный `main`, проверенный 2026-11-21. Ниже зафиксированы только выводы из исходного кода; это не утверждение о количестве строк или качестве данных в production.

### Подтверждённые пути чтения и записи

| Поверхность | Наблюдаемая зависимость | Классификация |
|---|---|---|
| `PatientPurchase.batch_id` и связь `batch` | Nullable FK на `product_batches.id` с `ON DELETE SET NULL`; свойства `batch_number` и `expiry_date` читают данные через связь | Историческая трассировка/чтение |
| `api/v1/patient_purchases.py` | Возвращает batch ID, номер партии и срок годности | Чтение API |
| `api/v1/dashboard.py` | Запрос истории препаратов пациента делает outer join с `ProductBatch`, чтобы показать срок годности исторической покупки | Чтение Dashboard |
| `api/v1/pharmacy_entities.py::list_batches` | Endpoint только для superuser выбирает строки `ProductBatch`, опционально фильтруя по продукту; pharmacy predicate отсутствует, поскольку у модели нет владельца-аптеки | Legacy административное чтение |
| `scripts/seed_database.py::seed_inventory` | Создаёт demo `ProductBatch` с начальным `available_quantity`; использует номер партии и expiry для создания/поиска pharmacy-scoped `Inventory` и записи opening movement | Demo/bootstrap запись |
| Связь `Product.batches` | ORM relationship остаётся доступной | Совместимость |

Проверенный seed path задаёт `ProductBatch.available_quantity` при создании отсутствующей demo-партии. Для уже существующей партии он обновляет метаданные срока годности, а связанная запись `Inventory` рассматривается как операционное состояние. Это не доказывает наличие безопасного dual-write протокола для production.

Endpoint списка партий ограничен `CurrentSuperuser`, но всё равно возвращает неограниченные по аптеке legacy-записи. Нельзя считать текущую проверку роли заменой pharmacy ownership или tenant-scoped доступу к остаткам. Отдельный frontend route партий сейчас не отображает страницу; это не удаляет backend endpoint и его API-контракт.

### Граница предметной области

- `Inventory` вместе с `InventoryMovement` — аптечный, tenant-scoped журнал партий и остатков.
- `ProductBatch` — глобальная/legacy-модель совместимости; она не должна определять доступный остаток, FEFO allocation, резервы или Edge synchronization.
- `PatientPurchase` — история пациента. Связь с партией является историческими метаданными, а не складским остатком.
- Историческая покупка должна оставаться понятной, даже если legacy-строка партии будет удалена. Текущий `ON DELETE SET NULL` может обнулить связь, оставив только запись покупки; этого недостаточно для гарантированного сохранения истории.

### Безопасная последовательность вывода из эксплуатации (проект решения; ещё не реализована)

1. **Заморозить контракт legacy-остатка.** Запретить новому операционному коду читать или изменять `ProductBatch.available_quantity` как источник складской истины. Поле временно сохранить для совместимости, пока не учтены все читатели и писатели.
2. **Добавить неизменяемые snapshot-поля покупки.** Добавить nullable snapshot-поля в `PatientPurchase` для номера партии/лота и срока годности на момент отпуска. Заполнить их из связанной партии, где она существует. Если связи нет — сохранить null и отразить пробел в отчёте; не угадывать партию по текущему Inventory.
3. **Проверить dual-read.** Перевести историю/API/Dashboard на приоритет snapshot-полей с временным fallback на legacy relationship. Добавить тесты для удалённой/отсутствующей партии, null legacy reference и неизменности отображения истории.
4. **Сверить данные до изменения writers.** Сформировать сравнение legacy batch metadata с `Inventory` по аптеке/продукту/лоту; сравнивать количества только при доказуемом соответствии. Отдельно показывать unmatched, ambiguous, duplicate, expired и cross-pharmacy случаи. Не исправлять расхождения автоматически.
5. **Убрать небезопасную административную поверхность.** Заменить неограниченный по аптеке список партий запросом pharmacy-scoped `Inventory`/lot либо явно вывести legacy endpoint из эксплуатации после миграции потребителей. Superuser должен быть дополнительным permission, а не заменой tenant scope.
6. **Удалить связи в отдельном релизе.** Только после code search, проверки API-контрактов, migration tests и telemetry, подтверждающей отсутствие legacy read/write: удалить ORM relationship и FK отдельной forward-only миграцией. Snapshot-данные и отчёт миграции сохранить.

### Обязательные gates проверки

- Статический поиск доказывает отсутствие операционных записей в `ProductBatch.available_quantity` за пределами разрешённого compatibility/seed пути.
- Unit/API-тесты доказывают сохранность истории пациента при отсутствии legacy batch.
- Tenant-тесты доказывают, что аптека не может перечислить `Inventory`-партии другой аптеки.
- Тесты сверки покрывают one-to-one, unmatched, duplicate и ambiguous mapping.
- Migration tests выполняют upgrade с репрезентативной старой схемы и проверяют количество snapshot backfill, null rows и referential integrity.
- Репетиция миграции проводится на disposable staging database; состояние production и наличие резервных копий не предполагаются по исходному коду.

**Статус:** карта зависимостей частичная, основана на исходном коде. Snapshot migration, замена endpoint, сверка данных, production-запросы и production-миграции не выполнялись. Этот аудит не разрешает удаление ProductBatch.

## Уточнение статуса реализации — более поздняя версия исходного кода

Этот аудит фиксирует историческую базовую версию `main` на commit `3d436a1b2280cb1e6d88a6c0664a1acf9b2c6dc9`. Указанный в нём критический пробел — отсутствие сохраняемого POS checkout — был верен для той проверенной версии, но больше не описывает более поздний снимок исходного кода `c6d35b828c1958f1bcb9077bbd0b6a71ef94613b`.

В более поздней версии есть подключённый router `/api/v1/pos`, транзакционный checkout, записи sale/payment/receipt, FEFO allocation, inventory movement и outbox, подписанный payment webhook, а также интеграционные тесты в `tests/integration/test_pos_checkout.py`. Следовательно, backend-реализация POS уже прошла дальше первоначального предложенного этапа C.

Это **не** означает, что весь аптечный POS workflow завершён: активный React POS feature сейчас возвращает `null`; checkout не связан с проверкой пациента/рецепта; возвраты/refunds и сверка кассовой смены не подтверждены более поздним аудитом; отдельный endpoint приёмки серии не является lifecycle закупки и приёмки по заказу поставщику.

Актуальная матрица подтверждений по каждому процессу: [Трассировка реализации аптечных процессов](../workflows/PHARMACY_WORKFLOW_TRACEABILITY.ru.md). Это уточнение основано только на исходном коде; production runtime и база данных не проверялись.
