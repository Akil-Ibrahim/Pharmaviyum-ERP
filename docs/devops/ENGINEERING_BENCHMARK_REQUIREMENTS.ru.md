# Pharmaviyum ERP/CRM — инженерные benchmarks и требования к качеству

## Статус и назначение

Документ определяет контракт измерений для оценки Pharmaviyum ERP/CRM и Mortarium AI. Это спецификация тестирования и целевая операционная модель, **а не доказательство того, что тесты уже запускались или цели достигнуты**.

Повторяемые запуски выполняются в GitHub Codespaces/локальной разработке; инфраструктурные сценарии — в изолированном staging. Используйте только синтетические данные аптек, товаров и пациентов.

Плановый бизнес-сценарий (три физические/логические POS-кассы, один дополнительный выделенный компьютер в кабинете заведующего аптекой — всего четыре рабочих места/компьютера на аптеку — и 14-часовой рабочий день для посетителей: 08:00–22:00 по местному времени аптеки):

| Показатель | План |
|---|---:|
| Аптеки | 100 |
| Посетители в день на аптеку | 200 |
| Всего посетителей в день | 20 000 |
| Сотрудники | 6 на аптеку / 600 всего |
| Часы работы для посетителей | 14 часов в день (08:00–22:00 по местному времени аптеки) |
| Кассы POS (рабочие кассовые места) | 3 на аптеку / 300 всего |
| Выделенный компьютер в кабинете заведующего аптекой | 1 на аптеку / 100 всего |
| Всего физических рабочих мест/компьютеров (3 POS + кабинет заведующего) | 4 на аптеку / 400 всего |

Шесть сотрудников — это общий штат аптеки по всем ролям, а не шесть фармацевтов. Три кассовых workflow входят в эти шесть штатных позиций и не добавляются сверх них. В каждой аптеке также предусмотрен отдельный компьютер в кабинете заведующего, помимо трёх POS-касс; это дополнительное оборудование, а не сотрудник. Рабочее место заведующего не следует автоматически считать дополнительным одновременным пользователем или сессией. 14-часовое окно — часы обслуживания посетителей; подготовка к открытию и закрытие могут выполняться вне этого окна и должны моделироваться отдельно. Посетители не равны аутентифицированным пользователям, одновременным сессиям, API-запросам или AI-запросам. Объём AI-запросов и пиковая конкурентность не определены; их нужно установить по телеметрии пилота и репрезентативным нагрузкам, а не выводить из числа посетителей.

## 1. Правила измерений и доказательств

Каждый отчёт содержит SHA коммита и ветку; дату, окружение и версии runtime/зависимостей; команду и конфигурацию теста; профиль нагрузки, конкурентность, длительность и прогрев; версию, размер и происхождение синтетического датасета; расположение артефактов; определение метрики, единицу и агрегацию; результат, цель, статус и ограничения.

Статусы:

| Статус | Значение |
|---|---|
| MEASURED | Измерено выполненным тестом в указанном окружении |
| HISTORICAL | Измерено ранее; сохранены исходные дата, revision и ограничения |
| ESTIMATED | Рассчитано/смоделировано, но не наблюдалось |
| NOT TESTED | Тест не выполнялся |
| UNAVAILABLE | Инструменты, данные или зависимости недоступны |
| NOT APPLICABLE | Метрика неприменима к компоненту |

Недоступное нельзя представлять как ноль. Не объединяйте результаты разных окружений или датасетов без указания различий. Результаты Codespaces не доказывают production capacity.

## 2. Производительность backend и API

Измеряйте по классам маршрутов и нагрузок: RPS; задержки p50/p90/p95/p99; доли HTTP 4xx и 5xx (раздельно клиентские и серверные); timeout и cancellation; число одновременных запросов; event-loop lag для async-нагрузок; CPU, память, сеть и перезапуски; насыщение ресурсов и ожидание в очередях.

Показывайте задержку успешных запросов и общую долю ошибок. Не исключайте неудачные запросы и timeout из знаменателя.

## 3. PostgreSQL, pgvector и Redis

### PostgreSQL / SQLAlchemy / Neon

Измеряйте задержки запросов p50/p95/p99 по классам, число медленных запросов и регрессии query plans, размер пула и занятые соединения, время ожидания и pool timeout, успешность транзакций, deadlocks и lock wait, CPU/память/I/O/насыщение соединений, задержку pgvector retrieval, просмотренные и возвращённые строки, поведение индексов и планов.

### Redis-совместимый сервис

Измеряйте задержки команд p50/p95/p99, частоту операций, ошибки и timeout, cache hit ratio = hits / (hits + misses), память, eviction, отклонённые подключения, активные соединения и ожидание пула, глубину очереди Celery broker, возраст старейшего сообщения, длительность задач, retries и failures. Cache hit ratio осмыслен только для определённой cache-нагрузки; не применяйте его ко всем Redis-командам.

## 4. Оценка RAG

Используйте Ragas с зафиксированной версией для поддерживаемых метрик ответа и контекста, а также детерминированные retrieval-метрики и собственные evaluators проекта. API и доступность метрик зависят от версии Ragas: проверяйте установленную версию и используйте поддерживаемый API.

### Retrieval metrics

По вручную размеченным релевантным ID чанков оценивайте Recall@K, Precision@K, Hit Rate@K, MRR, nDCG@K и при необходимости MAP@K. Указывайте K, число размеченных запросов, обработку неразмеченных запросов и revision корпуса/индекса. Существующий evaluator в src/pharmaviyum/ai/mortarium_rag/quality_metrics.py следует проверить и повторно использовать при необходимости.

### Ragas: метрики ответа и контекста

Используйте поддерживаемые установленной версией Faithfulness, Answer Relevancy, Context Precision, Context Recall, Context Entity Recall, Noise Sensitivity, Answer Correctness и Semantic Similarity. Фиксируйте версию Ragas, реализацию метрики, модель/версию judge, prompts, схему датасета и конфигурацию evaluator. LLM-as-judge — сигнал оценки, а не клиническая истина; калибруйте его на экспертно проверенных примерах.

### Метрики цитирования

Добавьте собственные детерминированные проверки:
- Citation Validity — ID источников существуют в извлечённых доказательствах.
- Citation Precision — доказательства поддерживают утверждение, к которому приложены.
- Citation Recall — фактические утверждения, требующие доказательств, имеют достаточные ссылки.
- Citation Correctness — эксперт подтверждает, что источник действительно обосновывает утверждение.

Ссылка на существующий чанк может быть валидной, но не обязательно корректной по смыслу.

## 5. Аптечные, клинические и лекарственные метрики

Это собственные доменные метрики, а не предполагаемые встроенные метрики Ragas. Используйте эталонные ответы, проверенные фармацевтами, и структурированные ожидаемые сущности. Точные совпадения и клинически эквивалентные варианты оценивайте отдельно.

Метрики: Medication Entity Accuracy; Active Ingredient Accuracy; Strength/Concentration Accuracy; Dosage Accuracy; Dosage Form Accuracy; Route of Administration Accuracy; Frequency/Duration Accuracy; Negation Preservation; Contraindication Recall; Drug Interaction Accuracy; Clinical Hallucination Rate; Unsupported Clinical Claim Rate; Source Attribution Accuracy; корректность эскалации для небезопасных или выходящих за рамки вопросов.

Сохраняйте различия между названием препарата, действующим веществом, концентрацией, дозой, формой, путём введения, частотой, длительностью, популяцией и отрицанием. Правильное название при неверной дозировке не является правильным ответом. Для каждой метрики укажите единицу анализа, знаменатель, правила сопоставления, adjudication и доверительный интервал, если позволяет выборка. Клинические пороги утверждают квалифицированные специалисты; универсальные проценты не придумываются.

## 6. Агент, LangGraph, Agent Harness и MCP

Измеряйте детерминированные наборы задач и исполнения, подтверждённые traces: Task Completion Rate; точность маршрутизации workflow; Tool Selection Accuracy; Tool Execution Success Rate; Tool Argument Accuracy; Agent Step Accuracy; Replanning Rate; Loop/Repeated-step Rate; Escalation Accuracy; retries и timeout; end-to-end и per-step latency; токены и стоимость успешной задачи, если доступны данные провайдера.

Успешный вызов инструмента не доказывает бизнес-результат. Независимо проверяйте конечное состояние и авторизацию. Добавляйте негативные тесты для запрещённых инструментов и неверных аргументов.

## 7. Безопасность, приватность и tenant isolation

Проводите синтетические adversarial-тесты на утечки между tenant при retrieval/ответах, обход RBAC и несанкционированное чтение/запись, неразрешённые MCP-вызовы, prompt injection во входе и извлечённых документах, утечки PII/клинических данных в ответы/logs/traces/labels, подмену tenant context и секреты в логах/артефактах.

Блокирующие релиз инварианты: ноль подтверждённых утечек между tenant; ноль несанкционированных запусков защищённых tools; ноль секретов или чувствительных данных пациентов в экспортируемой телеметрии; все критические тесты авторизации проходят. Это жёсткие gates, а не усредняемые баллы. Любое подтверждённое нарушение блокирует релиз до исправления и повторной проверки.

## 8. OpenTelemetry и наблюдаемость

Измеряйте покрытие traces критических путей, parent/child spans и W3C trace-context propagation, статус ошибок span и видимость исключений, покрытие метриками, корреляцию logs/traces по trace/span ID, сбои exporter/collector и потерю telemetry, проверку alerts и доставку уведомлений, MTTD/MTTR в контролируемых учениях.

Отслеживайте FastAPI, SQLAlchemy/PostgreSQL, Redis, Celery, LangGraph, RAG, MCP и внешние вызовы моделей там, где это поддерживается. Автоматическая instrumentation FastAPI не доказывает полного покрытия.

Не экспортируйте имена/ID пациентов, рецепты, raw prompts/completions, клинический текст, credentials или tokens. Не используйте tenant/user/session ID в Prometheus labels. Применяйте bounded-cardinality attributes и route templates, контроль доступа, retention и региональные правила хранения. Audit бизнес-действий отделяйте от диагностических traces.

## 9. Frontend и E2E

Используйте Vitest и Playwright, если доступны. Измеряйте pass/fail unit/component и E2E, покрытие критических workflow, ошибки навигации/API, browser console, успешность frontend build, размер bundle и пользовательскую задержку сценариев.

Критические сценарии: authentication/authorization, поиск товара, POS order flow, складские операции и рабочие процессы фармацевта/менеджера. Не заявляйте покрытие POS checkout, если API не выполняет реальный checkout, оплату, распределение партий и списание остатков.

## 10. Нагрузка, стресс и capacity

Используйте существующую точку входа k6 и документированные route contracts. Запускайте только локально или в изолированном staging на синтетических данных. По умолчанию тесты read-only. Запись требует явного opt-in, одноразовых staging-данных и проверенной очистки.

Ступени конкурентности 25, 50, 100, 250, 500 и 1 000 — профили стресс-тестов, а не прогноз одновременных пользователей или AI-запросов. Реалистичные arrival rates и пользовательские сценарии определяйте по pilot traffic.

Разделяйте нагрузки: интерактивные ERP/API reads; транзакционные записи и POS; поиск и склад; RAG/AI с отдельным контролем стоимости провайдера и конкурентности; фоновые ingestion и Celery jobs.

Отчитывайтесь об устойчивом throughput, percentiles задержек, ошибках/timeout, росте очередей, насыщении БД/cache, CPU/памяти, восстановлении после нагрузки и стоимости, если доступна. Дорогой AI-трафик не должен скрывать задержки основного ERP. План для 100 аптек — бизнес-допущение; capacity выводы требуют измеренного состава нагрузки, пиков, request rates, транзакций, AI-спроса и лимитов инфраструктуры.

## 11. Quality gates и релизная политика

Поддерживайте независимые gates: backend/API; БД/cache; retrieval; ответы и citations; клиническая безопасность; agent/MCP; security/tenant isolation; observability; frontend/E2E; scalability/recovery. Не сводите всё к среднему баллу.

Критические нарушения безопасности, tenant isolation, приватности и клинической безопасности блокируют релиз. Регрессии RAG/agent сравниваются с версионированной baseline и risk-specific thresholds. Performance thresholds устанавливаются по staging baseline и бизнес-SLO, а не по Codespaces. Каждый evaluation run фиксирует версии dataset, кода, prompts, модели, embeddings и индекса. Неизмеренное получает NOT TESTED или UNAVAILABLE, но никогда PASS.

## 12. Инструменты и границы окружений

| Инструмент | Назначение |
|---|---|
| pytest | Unit, integration, security и детерминированные evaluation-тесты |
| Ragas | Поддерживаемые метрики ответов и контекста RAG |
| Project retrieval evaluator | Recall@K, Precision@K, MRR, nDCG и retrieval latency |
| Locust / k6 | Контролируемые нагрузочные/стресс-тесты; предпочтителен имеющийся k6 workflow |
| Playwright / Vitest | Browser E2E и frontend-тесты |
| OpenTelemetry | Distributed traces, metrics и коррелированная telemetry |
| Prometheus / Grafana | Хранение/запрос метрик и dashboards |
| Tempo / Jaeger | Хранение и анализ traces в зависимости от стека |
| Loki | Централизованные логи, если развёрнут |
| LangSmith / Arize Phoenix | Необязательный UI для LLM traces/evaluation; не нужен при наличии эквивалентных средств |

Codespaces может проверять структуру, конфигурацию, зависимости, доступные тесты, детерминированные RAG/agent/MCP evaluations с fixtures/mocks, синтетические security/tenant тесты, локальную instrumentation и ограниченные benchmarks с фиксацией ресурсов. При доступных Compose-сервисах возможны локальные API/DB/cache тесты.

Codespaces сам по себе не доказывает capacity для 100 аптек, производительность FastAPI Cloud или managed Neon/Redis в production, реальные задержки/квоты/стоимость внешнего LLM без настроенного и контролируемого провайдера, production availability, доставку alerts, recovery objectives, региональное хранение или клиническую корректность без экспертной проверки.

Инфраструктуру и capacity проверяйте в изолированном staging с production-подобными лимитами и синтетическими данными. Не используйте реальные production-данные пациентов.

## 13. Обязательный benchmark-отчёт

Для каждой метрики указывайте: название/определение; статус MEASURED/HISTORICAL/ESTIMATED/NOT TESTED/UNAVAILABLE/NOT APPLICABLE; значение и единицу либо причину недоступности; утверждённую цель или «не определена»; окружение Codespaces/local Compose/staging/production; commit SHA; длительность, конкурентность, rate и сценарий; версию и размер датасета; команду, тест и артефакт; ограничения mocks/зависимостей/выборки; follow-up с ответственным, действием и приоритетом.

Отчёт завершается приоритизированным backlog и явным указанием, что доказано, а что нет. Production-readiness нельзя подтверждать только статическим аудитом кода или запуском в Codespaces.
