# Pharmaviyum ERP/CRM — архитектура AI

## Назначение

Документ описывает архитектуру AI, фактически реализованную в `src/pharmaviyum/ai` и доступную через приложение FastAPI.

Слой AI является частью основного backend и развёртывается вместе со стеком приложения.

## Архитектура во время выполнения

```text
Клиент / Frontend
       |
       v
FastAPI API (`src/pharmaviyum`)
       |
       +--> Аутентификация + контекст tenant
       |
       +--> AI API (`/api/v1/ai/...`)
               |
               +--> Agent Harness
               |      +--> маршрутизация моделей / LLM
               |      +--> память диалога
               |      +--> защитные механизмы (guardrails)
               |      +--> кеш
               |
               +--> RAG-граф
               |      +--> преобразование запроса
               |      +--> tenant-safe поиск
               |      +--> оценка документов
               |      +--> контекстное сжатие
               |      +--> генерация с цитированием источников
               |
               +--> уровень инструментов MCP
               |
               +--> наблюдаемость / метрики
               |
               +--> PostgreSQL + pgvector
               +--> Redis
               +--> Ollama / настроенный LLM-провайдер
```

## RAG

Текущая реализация RAG находится в `src/pharmaviyum/ai/mortarium_rag/`.

### Гарантии поиска

- Поиск ограничивается контекстом аутентифицированной аптеки/tenant.
- Страна и язык передаются в контексте запроса.
- Перед генерацией найденные документы рассматриваются как недоверенный ввод.
- Стабильные идентификаторы источников имеют формат `src-{chunk_uuid}`.
- `RAGResponse` при необходимости формирует цитаты на основе возвращённых источников.
- Метрики поиска не содержат идентификаторов tenant, пользователя или сессии с высокой кардинальностью.

### Границы доверия в prompt агента и памяти

Политика агента передаётся в отдельном `SystemMessage`. Метаданные аутентифицированного запроса, историческая память Redis, доказательства RAG и результаты инструментов остаются недоверенным содержимым в human/tool-сообщениях; их нельзя интерполировать в сообщение системной политики. Перед последним запросом пользователя агент добавляет отдельное сообщение `untrusted_reference_context`.

Маршрутизация намерений и суммаризация памяти также используют отдельные системные сообщения и сообщения с данными. Управляемые пользователем разделители экранируются до сборки структурированного контекста.

### Pipeline

```text
Запрос
  -> transform_query
  -> retrieve
  -> grade_documents
  -> compress
  -> generate
  -> guardrails
```

Граф требует явно настроенного checkpointer на базе PostgreSQL. **Идентификаторы checkpoint в двух графах различаются:** `PharmacistAgent._thread_id()` использует версионируемый дайджест HMAC-SHA-256 на основе идентичности аптеки, пользователя и потока; `LangGraphRAG._thread_id()` сейчас возвращает открытый составной идентификатор `rag:{pharmacy_id}:{user_id}:{raw_session_id}`. Поэтому ключ checkpoint RAG ограничен tenant, но не является непрозрачным. Прежнее утверждение, что оба графа используют HMAC-идентификаторы, было неверным. См. [текущий аудит Mortarium](./rag_architecture_audit.md) и пункты устранения P0/P1.

Пространства имён памяти диалога Agent Harness в Redis используют версионируемые HMAC-SHA-256 ключи, производные от session ID, ограниченного API. Это псевдонимизирует только имена Redis-ключей, но не шифрует содержимое диалогов. Защита транспорта Redis, контроль доступа, шифрование при хранении и правила хранения данных остаются обязательными задачами инфраструктуры.

HMAC-идентификаторы checkpoint агента и пространств имён памяти не возобновляют автоматически записи, созданные под прежними открытыми форматами ключей. При запуске приложения существующие записи не переписываются. Для памяти установлен ограниченный TTL в семь дней, однако TTL не является полной политикой хранения и удаления PHI. Payload checkpoint может содержать вопросы и найденный клинический контекст; сроки хранения, удаление, истечение резервных копий и поведение восстановления являются отдельными обязанностями жизненного цикла PHI.

**Ограничение области пациента:** область API-сессии и идентификаторы потоков обоих графов сейчас включают аптеку/пользователя/сессию, но не ID пациента. Повторное использование сессии при переключении пациентов может повторно использовать память диалога и состояние checkpoint. Нельзя заявлять о полной изоляции контекста пациента, пока привязка сессии или отклонение смены области не реализованы и не проверены регрессионными тестами.

### Загрузка документов (ingestion)

Загрузка документов, используемая API, реализована в `src/pharmaviyum/ai/mortarium_rag/ingestion` и запускается через Celery worker проекта. API авторизует tenant аптеки до отправки задачи; worker проставляет канонические метаданные tenant/источника до разбиения на чанки и сохранения векторных данных.

Отдельный класс `IngestionOrchestrator` создаётся при инициализации AI-зависимостей, однако в ходе этого аудита не найден вызывающий его API-код. Его прямой метод ingestion явно не проставляет те же метаданные tenant перед fail-closed upsert в vector store. До согласования или удаления неиспользуемого orchestrator каноническим следует считать путь через Celery task.

Не документируйте отдельное Kubernetes-развёртывание ingestion: в репозитории больше нет дерева Kubernetes-манифестов.

## Оценка RAG и аптечного AI

Метрики ранжирования retrieval и offline-синтетический benchmark описаны в [результатах Stage 1 AI RAG](./devops/STAGE_1_AI_RAG_OFFLINE_RESULTS.md). Переиспользуемый evaluator поиска сейчас рассчитывает Recall@K, Precision@K, MRR и nDCG по размеченным ID релевантных чанков. Расширенный контракт оценки находится в [требованиях к инженерному benchmark](./devops/ENGINEERING_BENCHMARK_REQUIREMENTS.md).

Ragas 0.4.3 объявлен в группе зависимостей `eval` в `pyproject.toml`, зафиксирован в `uv.lock` и лениво загружается через `src/pharmaviyum/ai/evaluation/ragas_adapter.py`; это не runtime-зависимость production. CI-задача оценки RAG устанавливает эту группу командой `uv sync --frozen --group eval`, проверяет импорт API collections Ragas и запускает тесты адаптера/unit и golden dataset. Тесты адаптера подменяют классы метрик Ragas, поэтому они проверяют API/контракт, а не измерение с реальной judge-моделью.

Специализированные аптечные проверки — название/дозировка/форма препарата, отрицания, изоляция контекста пациента, подтверждение цитатами и клинические галлюцинации — реализованы как проектные evaluators в `src/pharmaviyum/ai/evaluation/clinical_metrics.py`. Для них нужны размеченные синтетические или деидентифицированные данные, а для проверки поддержки утверждений — независимый judge. Эти пользовательские метрики не являются встроенными метриками Ragas.

Результаты оценки должны указывать версии набора данных, модели, prompt, embedding и индекса, размер выборки и среду выполнения. Нарушения безопасности и изоляции tenant являются самостоятельными блокирующими условиями релиза и не должны усредняться в общий показатель качества. Evaluator поддерживает отдельные оценки retrieval для русского и английского языков, однако текущие значения по умолчанию приложения, RAG и ingestion не включают русский язык; следовательно, поддержка RU и её качество пока не подтверждены. См. текущий [аудит Mortarium](./rag_architecture_audit.md).

## Ограничения runtime

- `PgVectorStore` выполняет векторный поиск и полнотекстовый поиск PostgreSQL с reciprocal-rank fusion. `RerankerPort` является необязательным, но текущий runtime `AIComponents` не внедряет конкретный reranker; `RAG_RERANK_TOP_N` не является действующим runtime-параметром.
- `RAG_ENABLE_CONTEXTUAL_COMPRESSION` объявлен, но не передаётся в `LangGraphRAG`; узел compression всегда присутствует в скомпилированном графе. `RAG_RRF_K`, `RAG_DEFAULT_LANGUAGES`, `RAG_MAX_CHUNK_TOKENS` и `RAG_CHUNK_OVERLAP` также требуют проверки связки конфигурации с runtime. Текущая Celery-задача ingestion использует значения конкретной задачи с жёстко заданными значениями по умолчанию для размера чанка и overlap.
- Model router использует эвристики длины запроса, ключевых слов и контекста. Это не валидированный классификатор клинического риска. Текущие поля confidence и safety score API — фиксированные эвристики представления, зависящие от предупреждений, а не калиброванные клинические вероятности.

## Agent Harness и память

Agent Harness обеспечивает прикладную оркестрацию вызовов LLM.

Текущие обязанности:

- маршрутизация моделей;
- память диалога;
- защитные механизмы;
- кеширование;
- доступ к инструментам;
- наблюдаемость.

Память диалога поддерживает сжатие сводок/фактов и хранение недавних сообщений. Harness передаёт настроенную основную LLM агента в суммаризацию памяти, вместо создания скрытого второго LLM-клиента.

Память ограничена аутентифицированной API-сессией и поддерживает операции TTL/trim/clear.

## Инструменты MCP

Реализация MCP находится в `src/pharmaviyum/ai/mcp`.

Она предоставляет сервер JSON-RPC 2.0 и реестр инструментов/ресурсов. Авторизация MCP интегрирована с ролями приложения и членством в аптеке.

MCP — внутренний компонент приложения, а не отдельный сервис верхнего уровня развёртывания.

## Поверхность API

AI endpoints реализованы в `src/pharmaviyum/api/v1/ai.py`.

Сейчас API предоставляет запросы и streaming, операции, связанные с ingestion, а также интеграцию AI health/metrics. Точные схемы запросов и ответов следует брать из FastAPI OpenAPI, а не копировать в этот документ.

Локальная документация API:

- Swagger UI: `http://localhost:8000/docs`
- OpenAPI JSON: `http://localhost:8000/openapi.json`
- Метрики: `http://localhost:8000/metrics`

## Наблюдаемость

Слой AI/RAG использует метрики приложения и необязательные интеграции трассировки.

Важные метрики RAG включают общее количество retrieval-операций и задержку поиска. Метки метрик намеренно имеют низкую кардинальность; не добавляйте `session_id`, ID пользователей, аптек и подобные идентификаторы в метки Prometheus. Spans узлов RAG записывают ограниченные количества и результаты, но не prompts и не клинические payload. Наличие instrumentation не доказывает, что OTLP exporter, collector, оповещения и политика хранения активны в каждом deployment.

В репозитории также есть конфигурация Prometheus/Grafana в `docker/`. Границы instrumentation OpenTelemetry, распространение trace context, правила защиты данных и критерии приёмки наблюдаемости описаны в [документации OpenTelemetry](./observability/opentelemetry.md).

## Данные и инфраструктура

Стек разработки Docker Compose по умолчанию сейчас предоставляет:

- PostgreSQL 18 с pgvector 0.8.7;
- Redis 8.8.4;
- Ollama;
- FastAPI API;
- Celery worker для ingestion;
- локальные сервисы наблюдаемости, если они настроены.

Это временные среды разработки. Отдельный профиль `docker-compose.prod.yml` остаётся на PostgreSQL 16 и Redis 7 до отдельно утверждённых миграций данных. Управляемые production-базы/кеши и Pharmacy Edge PostgreSQL 16/Valkey — отдельные среды; изменение development Compose stack не обновляет их.

FastAPI Cloud является целевой платформой размещения приложения. GitHub Actions обеспечивает CI и вручную запускаемый workflow deployment; базы данных, кеш и другие необходимые сервисы должны быть подготовлены и настроены отдельно.

В репозитории нет отдельного Kubernetes deployment для AI; Mortarium остаётся прикладным AI-слоем.

## Профили развёртывания LLM

Mortarium использует разные LLM-профили в зависимости от целевой среды.

| Профиль развёртывания | LLM-провайдер | Профиль модели | Статус / граница |
|---|---|---|---|
| Демо FastAPI Cloud | QwenCloud API | `qwen3.8-flash` | Только demo-профиль; действуют ограничения бесплатной квоты и настройки Free quota в консоли провайдера. |
| Ansible / локальная production-среда | Локальный runtime Ollama | `Qwen3.5 9B Q4_K_M` | Целевой профиль; проверка оборудования и production rollout ещё не завершены. |

Это намеренно раздельные профили. Demo-ключ QwenCloud, предположения о квотах и cloud API-конфигурацию нельзя копировать в production Ansible inventories. Целевая локальная production-среда выполняет inference через Ollama; её возможности ограничены CPU/GPU, RAM, диском и concurrency выбранного узла. Основной production AI runtime планируется для Central; локальный inference на Edge необязателен и должен быть явно утверждён для конкретного аппаратного профиля. POS и другие детерминированные аптечные транзакции никогда не должны зависеть от доступности Mortarium.

См. [эксплуатацию демо QwenCloud](./ai/QWENCLOUD_DEMO.md) и [развёртывание Pharmacy Edge через Ansible](./devops/PHARMACY_EDGE_ANSIBLE_ROLLOUT.md). Описание профиля не является доказательством завершённого live deployment.

## Конфигурация

Для локальной конфигурации используйте `.env.example`, а `.env.prod.example` — как справочник production-конфигурации.

Текущий источник истины для Python-зависимостей: `pyproject.toml` содержит прямые объявления зависимостей, а `uv.lock` — разрешённые версии. CI устанавливает зафиксированное окружение командой `uv sync --frozen`. Не создавайте второй авторитетный список зависимостей или отдельный файл `requirements-ai.txt`.

## Локальный запуск

```bash
cp .env.example .env

docker compose up --build
```

Или запустите API напрямую после установки зависимостей:

```bash
uv sync --frozen
uv run alembic upgrade head
uv run uvicorn src.pharmaviyum.main:app --reload --port 8000
```

## Принципы проектирования

1. Изоляция tenant обеспечивается до поиска и генерации.
2. Вывод LLM не считается источником истины; авторитетными остаются найденные источники и guardrails.
3. Для цитирования источников используются стабильные идентификаторы чанков.
4. Production deployment имеет один канонический путь релиза.
5. Документация описывает реализованное поведение, а не запланированную инфраструктуру.
