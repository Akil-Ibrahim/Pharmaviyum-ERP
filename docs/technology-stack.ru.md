# Технологический стек и глоссарий

[English](technology-stack.md) · **Русский**

В этом разделе объясняется не только, какие технологии используются в Pharmaviyum, но и зачем они нужны и за какую часть системы отвечают. Указанные версии — это декларации репозитория; сами по себе они не доказывают, что каждая зависимость активна во всех production-средах.

| **Redis Python client 8.1.0** | Python-библиотека клиента для Redis-совместимых серверов. | Позволяет backend-сервисам и worker-процессам взаимодействовать с настроенной Redis-совместимой инфраструктурой. |
| **Полнотекстовый поиск PostgreSQL** | Встроенный в БД лексический поиск по текстовым документам. | Дополняет векторное сходство в гибридном RAG-поиске и помогает находить точные названия препаратов, идентификаторы и фразы. |

**Разделение сред:** FastAPI Cloud используется только для публичной Demo с отдельными data services и синтетическими данными. Production развёртывается через Ansible на аптечном сервере; PostgreSQL и supporting services запускаются согласно утверждённому Pharmacy Edge profile. Версии сервисов Production подтверждаются по фактическому runtime аптечного сервера, а не по metadata Demo-провайдера. Локальный development/CI Compose является disposable-средой и не должен считаться Production deployment. Legacy-файл `docker-compose.prod.yml` с PostgreSQL 16/Redis 7 не является утверждённым путём для Production или Demo. См. [политику версий](#политика-версий-и-управление-зависимостями) и [границу deployment](deployment/PRODUCTION_DEMO_INFRASTRUCTURE_BASELINE.ru.md).

### 5. Mortarium AI, LLM и архитектура агентов

**Mortarium** — AI-слой поддержки принятия решений для фармацевта внутри Pharmaviyum. Он использует разрешённый контекст приложения и поиск по источникам, чтобы помогать специалистам находить, обобщать и интерпретировать релевантную информацию. Это рекомендательная система: разрешения, расчёты, остатки, платежи и решения об отпуске остаются под контролем детерминированных сервисов приложения.

| Технология / понятие | Определение | Для чего используется в Pharmaviyum |
|---|---|---|
| **AI-слой** | Подсистема приложения, объединяющая модели, retrieval, orchestration, инструменты, проверки политик и оценку качества. | Даёт фармацевту контролируемого AI-помощника, встроенного в ERP-процессы, а не изолированный универсальный чат-бот. |
| **LLM (Large Language Model)** | Большая языковая модель, обученная понимать и генерировать естественный язык. | Интерпретирует вопросы фармацевта, обобщает найденные источники и формирует структурированные ответы с указанием источников. Выбор модели/провайдера задаётся конфигурацией; имя модели нужно брать из активной конфигурации развёртывания, а не выводить из списка библиотек. |
| **QwenCloud** | Настроенный профиль провайдера модели для текущей demo-конфигурации. | Предоставляет inference языковой модели в demo-профиле. Настройка demo-провайдера не является доказательством того, что такой же провайдер/модель используется в production или доступен там. |
| **LangChain 1.4.0** | Фреймворк и абстракции для объединения моделей, prompt, retriever и интеграций инструментов. | Предоставляет строительные блоки интеграций для AI-слоя. Сам по себе LangChain не является движком workflow агента или базой данных. |
| **LangGraph 1.2.21** | Фреймворк графовой оркестрации для stateful многошаговых LLM-workflow. | Координирует этапы Mortarium agent и RAG, условную маршрутизацию, решения о вызове инструментов, ограниченные повторы и checkpoint-состояние workflow. |
| **Agent (агент)** | Контролируемый программный workflow, в котором модель может выбирать следующий шаг или инструмент из разрешённого набора. | Позволяет Mortarium определить, нужен ли поиск, ответ на основе переданного контекста или разрешённый read-only инструмент. Что разрешено, определяет серверная политика, а не модель. |
| **Agent Harness** | Прикладной контрольный слой вокруг выполнения модели/агента: проверка входа, контекст авторизации, ограниченная память, prompt/cache-политика, маршрутизация моделей, проверка результата и telemetry. | Обеспечивает единые меры безопасности и эксплуатации вокруг вызовов LangGraph и LLM. В проекте это архитектурный/прикладной слой, а не утверждение об установленном отдельном продукте под названием «Harness AI». |
| **RAG (Retrieval-Augmented Generation)** | Подход, при котором перед генерацией ответа LLM получает найденные релевантные источники. | Обосновывает аптечные ответы утверждёнными документами и индексированными знаниями, а не только параметрами модели. Предполагается сохранение source ID/citations и области авторизации. |
| **Embeddings (векторные представления)** | Числовые векторные представления текста, отражающие семантические связи. | Представляют чанки документов и запросы, чтобы находить семантически близкую информацию даже при различиях в формулировках. Конкретная embedding-модель определяется активной runtime-конфигурацией. |
| **Vector search** | Поиск по сходству между embedding-векторами. | Находит семантически связанные чанки для RAG. |
| **Hybrid search** | Сочетание лексического/полнотекстового поиска и векторного поиска по сходству. | Совмещает точное совпадение названий препаратов, дозировок и идентификаторов с семантически близким текстом. |
| **Chunking (разбиение на чанки)** | Разделение исходных документов на небольшие фрагменты для поиска с сохранением полезного контекста и метаданных. | Удерживает найденный контекст в пределах лимитов модели и повышает релевантность. Текущий MedicalChunker поддерживает эвристики медицинских заголовков, группировку предложений и рекурсивный fallback; оценка токенов приблизительная, а не основанная на точном tokenizer. |
| **Фильтрация метаданных** | Ограничение поиска по доверенным атрибутам: аптека, уровень доступа, язык и источник документа. | Предотвращает поиск между аптеками и исключает данные конкретного пациента, если аутентифицированный запрос не имеет соответствующей области доступа. Отсутствующая или некорректная область доступа должна приводить к отказу (fail closed). |
| **MCP (Model Context Protocol)** | Протокол предоставления инструментов и ресурсов AI-приложениям через определённый клиент-серверный контракт; в проекте описан MCP-слой на базе JSON-RPC. | Даёт Mortarium контролируемый способ обнаруживать и вызывать разрешённые аптечные операции. Доступность инструментов фильтруется по ролям и проверяется сервером; аргументы, сгенерированные моделью, не устанавливают личность или права доступа. |
| **Prompt/context engineering** | Проектирование инструкций и выбор доверенного контекста, передаваемого модели. | Удерживает ассистента в рамках задачи фармацевта, юрисдикции, языка, выбранного контекста пациента и бюджета источников. |
| **Guardrails (защитные ограничения)** | Проверки входных/выходных данных и политики, ограничивающие поведение модели. | Отклоняют некорректную область доступа, ограничивают небезопасное использование инструментов, проверяют структуру ответа и позволяют безопасно воздержаться от ответа при недостатке или конфликте источников. |
| **Ragas 0.4.3** | Фреймворк оценки качества RAG на основе эталонных данных и моделей-оценщиков. | Измеряет offline-показатели: faithfulness, answer relevancy, context precision и context recall. Объявлен в группе зависимостей `eval` и используется в CI/evaluation jobs; не устанавливается в production runtime и не импортируется в production request path. |
| **Фармацевтические метрики качества** | Доменные проверки сверх общих LLM-оценок. | Проверяют подтверждение цитатами, название/дозировку/форму препарата, сохранение отрицаний, неподтверждённые клинические утверждения, изоляцию пациентов и поиск на русском/английском. Это регрессионные проверки, а не клиническая сертификация. |

**Важная граница AI:** RAG и агентные workflow не делают ответ клинически авторитетным. Доступ к данным пациента и аптеки обеспечивается кодом приложения и фильтрами retrieval. Ответственность за профессиональные решения остаётся у фармацевта. См. [проектирование Mortarium AI](./ai/AI_LLM_SYSTEM_DESIGN.md), [pipeline чанкинга](./ai/chunking-pipeline.md) и [оценку Ragas](./ai/ragas-pharmaceutical-evaluation.md).

### 6. Наблюдаемость и эксплуатация

| Технология | Определение | Для чего используется в Pharmaviyum |
|---|---|---|
| **OpenTelemetry 1.45.2** | Независимые от поставщика API, SDK и соглашения для telemetry, прежде всего распределённых трассировок. | Отслеживает ограниченные spans в API и Mortarium workflow, чтобы анализировать задержки и ошибки. В spans нельзя помещать чувствительные prompts, данные пациентов, токены и найденный клинический текст. |
| **OTLP** | OpenTelemetry Protocol для экспорта telemetry в collector/backend. | Передаёт трассировки приложения в настроенный telemetry collector. Наличие SDK само по себе не доказывает, что production-трассировки действительно доставляются. |
| **Prometheus** | Система сбора метрик и мониторинга временных рядов. | Собирает числовые метрики сервиса: число запросов, ошибки, длину очередей и гистограммы задержек. Метки должны иметь низкую cardinality и не содержать идентификаторы пациентов/пользователей. |
| **Grafana** | Платформа dashboard и визуализации метрик и других telemetry-источников. | Показывает операционные панели и помогает исследовать состояние и производительность сервисов. |
| **Jaeger** | Backend распределённой трассировки и интерфейс просмотра trace. | Предоставляет локальный просмотрщик spans и связей запросов в development Compose-стеке. |
| **OpenTelemetry Collector** | Независимый от поставщика сервис приёма, обработки и экспорта telemetry. | Отделяет instrumentation приложения от конечного trace backend и обеспечивает контролируемый telemetry pipeline. |

### Источники истины для зависимостей

Python-зависимости определяются в следующих файлах:

- `pyproject.toml` — прямые зависимости, optional groups и настройки инструментов.
- `uv.lock` — разрешённые и воспроизводимые версии Python-зависимостей.
- `[dependency-groups].eval` в `pyproject.toml` — изолированные зависимости оценки Ragas; устанавливаются явно для evaluation через `uv sync --group eval`. Эта группа исключена из установки production runtime.

Frontend-зависимости определяются в следующих файлах:

- `frontend/shadcn-admin/package.json` — frontend-зависимости и scripts.
- `frontend/shadcn-admin/bun.lock` — зафиксированные версии frontend-зависимостей.

Не создавайте второй авторитетный список Python-зависимостей. Меняйте зависимости в исходных manifest-файлах, обновляйте соответствующий lock-файл и запускайте проверки CI.

## Процедура обновления зависимостей

1. Измените прямые Python-зависимости и optional dependency groups (например, `eval`) в `pyproject.toml`.
2. Перегенерируйте и закоммитьте `uv.lock`; CI использует frozen sync, а RAG evaluation job устанавливает группу командой `uv sync --frozen --group eval`.
3. Измените frontend-зависимости в `frontend/shadcn-admin/package.json` и обновите отслеживаемый Git lock-файл `frontend/shadcn-admin/bun.lock`.
4. Запустите backend lint, форматирование, проверку типов, unit- и integration-тесты; затем frontend lint, форматирование, production build и тесты.
5. Для major-обновлений проверьте заметки о совместимости и security advisories.
6. Обновляйте этот документ и README только после изменения конфигурации репозитория. Не описывайте запланированное обновление как уже установленное.
7. Откройте pull request и проверьте результаты GitHub Actions до merge.

## Примечания по runtime-инфраструктуре

- Hosted Production использует подтверждённый проект Neon PostgreSQL 18; Demo должна использовать отдельную PostgreSQL 18. Disposable development/CI Compose также ориентирован на PostgreSQL 18 с pgvector 0.8.7.
- Приложение использует Python-клиент pgvector и расширение PostgreSQL для векторного поиска, если оно включено; это отдельно версионируемые компоненты.
- Hosted Production и Demo используют отдельные managed Redis endpoints. Redis 8.8.4 — целевая версия совместимости; точная версия managed-сервера контролируется провайдером и должна быть подтверждена по provider metadata до релиза. Disposable development/CI Compose использует Redis 8.8.4.
- Шаблон Ansible для Pharmacy Edge использует Valkey; этот серверный профиль намеренно отделён от локального Redis.
- Локальный Compose перехватывает исходящую почту приложения в Mailpit (`http://localhost:8025`, SMTP `localhost:1025`). См. [доставку электронной почты и локальное тестирование](./development/email.md). Для Demo-доставки необходимо явно задать SMTP host, port, sender, TLS mode и credentials в окружении Demo. Production SMTP настраивается в отдельной управляемой среде хостинга.
- Выбор LLM-провайдера/модели Mortarium задаётся переменными окружения. Текущий профиль развёртывания описан в [архитектуре AI](./ai_architecture.md) и [руководстве по FastAPI Cloud](./deployment/FASTAPI_CLOUD.md).
