# PY-001 — Основной вопрос

**Вопрос (RU):** Как Python выполняет программу: от исходного кода до поведения во время выполнения?

**Оригинальная формулировка (EN):** How does Python execute a program from source code to runtime behavior?

**Что проверяется**

- Понимание пути от исходного кода до выполнения программы.
- Умение различать семантику языка Python и детали реализации CPython.
- Знание parsing, AST, compilation, code objects, bytecode, namespaces и runtime execution.
- Способность применять эту модель при диагностике ошибок и анализе производительности.

**Коротко**

Исходный код Python разбирается и компилируется в исполняемое представление. В CPython этап parsing формирует абстрактное синтаксическое дерево (AST), а компиляция создаёт объекты кода (code objects), содержащие байткод и метаданные. Механизм исполнения CPython выполняет эти объекты кода в runtime-окружении, включающем объекты, пространства имён и состояние выполнения. В процессе могут вызываться Python-функции, нативные расширения и средства операционной системы.

Формат байткода и конкретный способ исполнения относятся к деталям реализации. Другие реализации Python могут использовать иные механизмы, сохраняя определённое языком поведение.

**Объяснение**

Удобно разделить выполнение программы на следующие этапы:

1. **Получение и декодирование исходного кода.** Интерпретатор получает исходный текст из файла или другого источника и декодирует его с учётом применимых правил кодировки.
2. **Parsing — синтаксический разбор.** Лексический и синтаксический анализ проверяет структуру программы и формирует AST. AST представляет выражения, присваивания, определения, импорты и конструкции управления потоком. Само по себе AST ещё не является конечным исполняемым представлением.
3. **Compilation — компиляция.** Компилятор анализирует области видимости и управление потоком, после чего создаёт объекты кода. Code object содержит исполняемые инструкции и метаданные: константы, имена, сведения о переменных и расположении исходного кода.
4. **Создание runtime-объектов.** При выполнении кода модуля Python создаёт объекты и связывает их с именами. Определение функции создаёт объект функции, который ссылается на скомпилированный код и контекст выполнения. Само определение функции не запускает её тело.
5. **Исполнение байткода в CPython.** Механизм исполнения CPython обрабатывает инструкции, вычисляет выражения, выполняет вызовы и управляет потоком выполнения. Конкретные opcode и оптимизации меняются между версиями CPython.
6. **Runtime-службы.** Выделение объектов, разрешение имён, импорт, распространение исключений, управление памятью и взаимодействие с нативными расширениями обеспечивают выполнение программы.
7. **Взаимодействие с операционной системой.** Работа с файлами, сокетами, процессами, сигналами и другими системными ресурсами в конечном счёте использует механизмы операционной системы.

CPython может сохранять скомпилированный байткод в каталоге `__pycache__` и повторно использовать действительный кеш при последующих импортах. Это оптимизация, а не обязательное требование языка Python. Файл `.pyc` не является исполняемым файлом с нативным машинным кодом.

**Как это работает**

- **AST:** структурированное представление синтаксиса исходного кода, используемое компилятором.
- **Code object:** скомпилированные инструкции и метаданные. Это не то же самое, что объект функции.
- **Function object:** runtime-объект, который оборачивает code object и хранит ссылки на контекст, например глобальное пространство имён, значения аргументов по умолчанию и состояние closure.
- **Frame / execution state:** состояние, необходимое для выполнения блока кода, включая ссылки на пространства имён и текущую позицию инструкции. Внутреннее представление может меняться между версиями CPython.
- **Evaluation machinery:** механизм CPython, который обрабатывает байткод и выполняет соответствующие операции. В современных версиях используются адаптивная специализация и другие оптимизации, детали которых зависят от версии.
- **Runtime services:** управление памятью, механизм импорта, обработка исключений и интеграция с нативными расширениями.

**Пример**

Рассмотрим код:

```python
RATE = 1.2

def calculate(amount: float) -> float:
    return amount * RATE

result = calculate(10)
```

Концептуально CPython компилирует код модуля и тело функции в объекты кода. При выполнении модуля имя `RATE` связывается со значением в пространстве имён модуля, создаётся объект функции `calculate`, и этот объект связывается с соответствующим именем. Последняя инструкция вызывает функцию. Во время вызова функция выполняет свой code object и разрешает имя `RATE` через соответствующее глобальное пространство имён.

**Пример анализа байткода**

```python
import dis

RATE = 1.2

def calculate(amount: float) -> float:
    return amount * RATE

print(calculate.__code__)
dis.dis(calculate)
```

Модуль `dis` позволяет исследовать байткод, который предоставляет текущий интерпретатор. Его вывод зависит от версии. Корректность приложения не должна зависеть от конкретной последовательности инструкций, если приложение намеренно не привязано к определённой версии интерпретатора и это не проверяется тестами.

**Практика**

- Сначала объяснять концептуальный процесс выполнения, а уже затем переходить к внутренним деталям.
- Разделять гарантии языка и особенности CPython.
- Использовать документированные инструменты интроспекции, например `dis` и `inspect`, для конкретной диагностики.
- При воспроизведении runtime-проблем фиксировать реализацию и версию интерпретатора.
- Рассматривать кеш байткода как оптимизацию, а не как контракт развёртывания.
- При диагностике импорта проверять entry point, имена модулей, рабочую директорию, `sys.path`, побочные эффекты и конфигурацию окружения.
- Предпочитать документированные публичные контракты предположениям, основанным на одной сборке интерпретатора.

**Компромиссы**

CPython — наиболее распространённая реализация для многих backend-нагрузок; она использует исполнение байткода и специфичные для реализации оптимизации. Другие реализации могут применять иные стратегии, включая JIT-компиляцию. Нативные расширения способны повысить производительность подходящих операций, но добавляют риски и затраты, связанные с упаковкой, ABI, безопасностью памяти и совместимостью. Предварительная компиляция или кеширование байткода могут сократить повторную работу компилятора, однако эффект может быть незначительным, если запуск приложения в основном ограничен импортами, I/O или инициализацией.

**Частые ошибки**

- Утверждать, что в Python нет этапа компиляции, потому что язык называют интерпретируемым.
- Предполагать, что каждая реализация Python исполняет байткод CPython.
- Считать названия opcode и последовательности байткода стабильными гарантиями языка.
- Путать code object с function object.
- Считать файлы `.pyc` нативными исполняемыми файлами.
- Забывать, что инструкции верхнего уровня обычно выполняются во время импорта модуля.
- Игнорировать нативные расширения, настройки runtime или поведение ОС при диагностике проблемы.

**Senior perspective**

Модель исполнения следует использовать как диагностическую основу, а не как набор фактов для заучивания. Нужно воспроизвести проблему на известной реализации и версии интерпретатора, а затем определить, относится ли она к семантике исходного кода, компиляции, импорту и инициализации, поведению runtime-объектов, нативной зависимости или операционной системе.

При оптимизации необходимо измерять реальную нагрузку. Оптимизация байткода бесполезна, если endpoint ожидает ответа базы данных, сети, блокировки или внешнего сервиса. Для переносимости следует опираться на документированную семантику Python и явно фиксировать зависимости от особенностей CPython.

**Ответ для интервью (RU)**

«Выполнение программы на Python состоит из нескольких этапов. Исходный код разбирается в структурированное представление, обычно AST, а затем компилируется в code objects. В CPython эти объекты содержат байткод и метаданные. Механизм исполнения интерпретатора выполняет байткод в контексте runtime-объектов и пространств имён, а runtime-службы обеспечивают вызовы функций, импорт, обработку исключений и управление памятью.

При выполнении модуля исполняются инструкции верхнего уровня и создаются привязки имён. Определение функции создаёт объект функции, который ссылается на скомпилированный код и контекст выполнения; тело функции выполняется при её вызове. Некоторые операции обращаются к native extensions или средствам операционной системы.

Я различаю семантику языка Python и детали реализации CPython. Формат байткода, названия opcode, внутреннее устройство frames и стратегии специализации могут меняться между версиями. Я использую такие инструменты, как `dis` и `inspect`, когда они помогают проверить конкретную гипотезу, но не строю корректность приложения на внутренних деталях интерпретатора».

# FU-001 — Этапы исполнения в CPython

**Вопрос (RU):** Какие основные этапы проходит исходный код Python до выполнения инструкций в CPython?

**Оригинальная формулировка (EN):** What are the main stages between Python source code and the execution of its instructions in CPython?

**Что проверяется**

Понимание parsing, compilation, исполнения байткода и runtime-поведения.

**Коротко**

CPython декодирует исходный текст, разбирает его в AST, компилирует AST в объекты кода с байткодом и метаданными, а затем исполняет эти объекты с помощью механизмов интерпретатора. По мере необходимости участвуют runtime-объекты, пространства имён, frames, встроенные функции, нативные расширения и службы ОС. Кеширование байткода может избавить от части повторной компиляции, но это оптимизация, а не обязательный этап языка.

**Объяснение**

Последовательность включает декодирование исходного кода, лексический и синтаксический анализ, построение AST, компиляцию в code objects, создание runtime-объектов и привязок имён, исполнение байткода и взаимодействие со службами runtime и ОС.

Тело функции компилируется вместе с содержащим её кодом, но обычно исполняется только при вызове функции. Выполнение инструкции определения функции создаёт объект функции и связывает его с именем.

**Как это работает**

Code object хранит исполняемые инструкции и метаданные. Function object ссылается на code object и runtime-контекст, например глобальное пространство имён и значения аргументов по умолчанию. Во время вызова CPython формирует состояние выполнения, необходимое функции. Представление frame, инструкции байткода и оптимизации механизма исполнения зависят от реализации и версии.

**Пример**

```python
def greet(name):
    print(f"Hello, {name}")

print("module initialization")
```

При выполнении модуля создаётся и связывается с именем функция `greet`, а также выполняется инструкция `print` на уровне модуля. Тело `greet` не выполняется до вызова этой функции.

**Практика**

Использовать анализ AST для изучения структуры исходного кода, а дизассемблирование — для анализа исполнения в CPython. Проверять версию интерпретатора. Не делать вывод, что тело функции выполняется только потому, что её определение было импортировано.

**Компромиссы**

Анализ AST полезен для инструментов работы с исходным кодом; анализ байткода помогает отвечать на вопросы, специфичные для CPython. Ни один из этих подходов сам по себе не объясняет внешние I/O-операции, нативные расширения или планирование процессов ОС. Следует выбирать наиболее узкий диагностический уровень, который подтверждается имеющимися данными.

**Частые ошибки**

- Смешивать parsing и исполнение.
- Предполагать, что тела функций выполняются во время импорта.
- Считать `__pycache__` обязательным.
- Предполагать, что байткод идентичен между версиями.

**Senior perspective**

При проблеме запуска сервиса нужно определить, возникает ли сбой на этапе parsing, разрешения импортов, инициализации модуля или обработки запросов. Это сужает область поиска и помогает не исследовать байткод, если реальная причина — отсутствующая зависимость, циклический импорт или побочный эффект верхнеуровневого кода.

**Ответ для интервью (RU)**

«CPython читает и декодирует исходный код, разбирает его в AST, а затем компилирует в code objects, содержащие байткод и метаданные. Интерпретатор выполняет эти объекты в runtime-контекстах, включающих пространства имён и объекты. Инструкции уровня модуля выполняются при запуске модуля, тогда как тело функции выполняется при вызове этой функции. Кеширование байткода является оптимизацией, а конкретный байткод и внутренние механизмы исполнения зависят от версии интерпретатора».

# FU-002 — Запуск файла как скрипта и импорт модуля

**Вопрос (RU):** Как бы вы исследовали ситуацию, когда модуль Python ведёт себя по-разному при запуске как скрипт и при импорте из другого модуля?

**Оригинальная формулировка (EN):** How would you investigate a case where a Python module behaves differently when run as a script versus imported by another module?

**Что проверяется**

Знание идентичности модуля, `__name__`, `__main__`, контекста пакета, путей импорта, рабочей директории и побочных эффектов во время импорта.

**Коротко**

Я сравниваю режимы выполнения и проверяю `__name__`, `__package__`, `__file__`, `sys.path`, рабочую директорию и точную команду запуска. При прямом запуске модуль обычно получает имя `__main__`, а при импорте используется его импортное имя. Это может менять условное выполнение кода, поведение относительных импортов, идентичность модуля и порядок инициализации.

Также я проверяю, не был ли один и тот же файл импортирован под разными именами, и не использует ли приложение рабочую директорию как неявную конфигурацию путей пакета.

**Объяснение**

При команде вида `python path/to/module.py` файл обычно выполняется как `__main__`, а его пакетный контекст может отличаться от контекста обычного импорта. При импорте Python разрешает имя модуля, проверяет `sys.modules`, находит loader, создаёт или получает объект модуля и при необходимости исполняет его код верхнего уровня.

Запуск пакетного модуля командой `python -m package.module` использует механизм импорта с учётом пакета и часто надёжнее для модулей, использующих относительные импорты.

Условие `if __name__ == "__main__":` выполняется при запуске файла как точки входа, но не при обычном импорте. Более тонкая проблема возникает, если один исходный файл загружается под двумя именами, например как `__main__` и как `package.module`. Python может создать два объекта модуля, из-за чего идентичность классов, реестры, предположения о singleton и состояние уровня модуля могут разойтись.

**Как это работает**

`sys.modules` кеширует модули по импортному имени. `__name__` определяет текущее имя модуля; `__package__` задаёт пакетный контекст для относительных импортов. `sys.path`, finders и loaders определяют, где и как модуль будет найден и загружен.

## Практическая диагностика

1. Зафиксировать точную команду, рабочую директорию, исполняемый файл Python и окружение.
2. Сравнить `__name__`, `__package__`, `__file__` и `sys.path` в обоих режимах.
3. Проверить, что ожидаемый корень пакета присутствует в пути импорта.
4. Проверить относительные импорты и побочные эффекты на уровне модуля.
5. Найти в `sys.modules` один и тот же исходный файл, загруженный под разными именами.
6. Воспроизвести запуск через предполагаемую точку входа пакета, часто `python -m package.module`.
7. Добавить тест импорта, проверяющий отсутствие нежелательных побочных эффектов.

**Практика**

Использовать понятную структуру пакета и документированную точку входа; не перегружать код верхнего уровня; помещать запускаемую логику в `main()` за стандартной проверкой `__name__`; не изменять `sys.path` без необходимости; не импортировать один исходный файл под несколькими именами.

**Компромиссы**

Прямой запуск файла удобен для самостоятельных скриптов. Запуск с учётом пакетного контекста надёжнее для модулей с относительными импортами. Установленная console-script entry point может обеспечить ясный операционный интерфейс для развёртываемого приложения.

**Частые ошибки**

- Предполагать, что `__name__` всегда равно имени пакета.
- Путать рабочую директорию с `sys.path`.
- Игнорировать обращения к базе данных или сети во время импорта.
- Добавлять произвольные изменения путей, не понимая последствий для идентичности модулей.

**Senior perspective**

Нужно стандартизировать одну точку входа для локальной разработки, тестов, контейнеров и production-развёртывания. Импорты должны быть детерминированными и не создавать лишних побочных эффектов. После этого запуск следует проверять в окружении, близком к production. Такой подход уменьшает количество ошибок, связанных с разными рабочими директориями и путями импорта.

**Ответ для интервью (RU)**

«Сначала я сравниваю контексты выполнения. При прямом запуске значение `__name__` обычно равно `__main__`, тогда как при импорте используется импортное имя модуля. Я проверяю `__name__`, `__package__`, `__file__`, `sys.path`, текущую рабочую директорию и точную команду запуска. Затем анализирую относительные импорты, побочные эффекты при импорте и вероятность загрузки одного файла под двумя разными именами. Для приложений с пакетной структурой я предпочитаю единый запуск с сохранением контекста пакета, например `python -m package.module`, либо установленную точку входа приложения».

# FU-003 — Гарантии языка и детали реализации

**Вопрос (RU):** Какие аспекты байткода и поведения интерпретатора являются деталями реализации, а не гарантиями языка, и почему это различие важно?

**Оригинальная формулировка (EN):** Which aspects of bytecode and interpreter behavior are implementation details rather than language guarantees, and why does that distinction matter?

**Что проверяется**

Переносимость, совместимость, понимание документированных контрактов и границы между семантикой Python и внутренним устройством CPython.

**Коротко**

Python определяет наблюдаемую семантику, например поведение выражений, протоколы объектов, исключения и документированное поведение встроенных типов. Но язык в общем случае не гарантирует конкретный формат байткода, последовательность opcode, структуру frame, устройство цикла интерпретации, стратегию подсчёта ссылок или механизм специализации. Зависимость от таких деталей может сделать код хрупким при обновлении интерпретатора или переходе на другую реализацию.

**Объяснение**

Гарантии языка — это поведение, требуемое спецификацией языка или документированными публичными API. Детали реализации — решения, принятые конкретным интерпретатором.

Примеры особенностей CPython:

- точные инструкции байткода;
- операнды opcode и inline caches;
- внутреннее представление frame;
- организация evaluation loop;
- поведение аллокатора;
- конкретная реализация подсчёта ссылок.

К документированной семантике относятся правила присваивания и вычисления выражений, правила вызова функций, обработка исключений, протоколы итераторов и контекстных менеджеров, а также специфицированное поведение встроенных типов.

Некоторое поведение может стать документированной гарантией в определённой версии языка. Поэтому инженер должен проверять документацию целевой версии, а не полагаться на неофициальные предположения.

Модуль `dis` показывает байткод текущего интерпретатора; это не контракт сериализации между версиями. Функция `sys.getsizeof` сообщает размер объекта, специфичный для реализации, и не измеряет весь граф объектов, достижимых из него.

**Пример**

Тест, который проверяет точную последовательность opcode в дизассемблированном коде, может завершиться ошибкой после обновления CPython, даже если наблюдаемое поведение программы не изменилось. Надёжный тест проверяет фактический контракт: возвращаемое значение, тип исключения или документированный побочный эффект.

**Практика**

- Зависеть от документированной семантики и публичных API.
- Фиксировать версию интерпретатора, если воспроизводимость этого требует.
- Изолировать оптимизации, специфичные для реализации.
- Разделять переносимые поведенческие тесты и тесты, зависящие от реализации.
- Повторно проверять предположения при обновлении интерпретатора.

**Компромиссы**

Внутренние механизмы CPython могут быть оправданы в профайлерах, отладчиках, runtime-инструментах или специализированных библиотеках. Компромисс — более тесная связанность с реализацией и более высокая стоимость сопровождения. Обычному прикладному коду следует отдавать предпочтение переносимым абстракциям.

**Частые ошибки**

- Считать дизассемблирование стабильным контрактом.
- Предполагать, что особенности управления памятью CPython применимы ко всем реализациям.
- Считать поверхностный размер объекта полным объёмом занимаемой им памяти.
- Заявлять о совместимости, не указывая реализацию и версию интерпретатора.

**Senior perspective**

Следует классифицировать каждое предположение: контракт языка, документированный контракт библиотеки, деталь конкретной реализации или наблюдаемая оптимизация. Использовать внутренние механизмы стоит только при наличии обоснования; такую зависимость необходимо изолировать, документировать и проверять на всех поддерживаемых версиях интерпретатора.

**Ответ для интервью (RU)**

«Python определяет поведение языка, но не стандартизирует каждый механизм, который интерпретатор использует для его реализации. В CPython инструкции байткода, внутреннее устройство frames, оптимизации цикла интерпретации, организация памяти и детали подсчёта ссылок относятся к реализации и могут меняться. Модуль `dis` показывает байткод текущего интерпретатора, но это не переносимый контракт.

Корректность приложения я основываю на документированном поведении языка и библиотек. Если я использую особенность CPython, то изолирую её, документирую зависимость от версии и проверяю при обновлениях».

# FU-004 — Выбор уровня диагностики production-проблемы

**Вопрос (RU):** Как при диагностике production-проблемы определить, нужно ли исследовать поведение на уровне Python, внутреннее устройство CPython или окружение операционной системы и runtime?

**Оригинальная формулировка (EN):** When diagnosing a production issue, how would you decide whether to inspect Python-level behavior, CPython internals, or the operating-system/runtime environment?

**Что проверяется**

Диагностику на основе доказательств, observability, анализ производительности и безопасное исследование production-систем.

**Коротко**

Я начинаю с наблюдаемого симптома, масштаба проблемы, временной последовательности и последних изменений. Собираю метрики, логи, трассировки и воспроизводимый пример, после чего перехожу от наиболее вероятной причины на высоком уровне к более низкоуровневым механизмам.

Поведение Python я исследую при проблемах бизнес-логики или состояния приложения. Внутренние механизмы CPython — когда данные указывают на поведение интерпретатора, память, байткод или runtime overhead. Уровень ОС и окружения — когда симптомы указывают на ограничения ресурсов, планирование, файловые дескрипторы, сокеты, сигналы или сбои процессов.

**Объяснение**

1. **Определить симптом:** неверный результат, сбой запуска, задержка, снижение throughput, рост памяти, завершение процесса или периодическая недоступность.
2. **Установить масштаб и baseline:** определить, затронут ли один процесс, хост, endpoint или все экземпляры; сравнить показатели с известным стабильным состоянием.
3. **Изучить данные приложения:** структурированные логи, трассировки, цепочки исключений, контекст запроса, время выполнения запросов к базе данных, вызовы зависимостей и недавние изменения.
4. **Исследовать Python runtime при наличии оснований:** профилирование, stack traces, состояние потоков, `tracemalloc`, диагностику garbage collection, дизассемблирование, версию интерпретатора, startup flags и загруженные расширения.
5. **Проверить ОС и контейнер:** throttling CPU, лимиты памяти и OOM-события, количество процессов и потоков, лимиты файловых дескрипторов, состояние диска, сетевые ошибки, DNS, состояние сокетов, сигналы и конфигурацию контейнера.
6. **Проверить гипотезы:** по возможности менять одну релевантную переменную, воспроизводить проблему под репрезентативной нагрузкой и сравнивать измерения.
7. **Исправить и предотвратить повторение:** применить минимальное безопасное исправление, проверить функциональность и производительность, добавить инструментацию или регрессионные тесты.

Эти уровни взаимосвязаны. Видимая утечка памяти Python может быть вызвана неограниченным кешем, удерживаемыми ссылками, нативными аллокациями, поведением аллокатора или лимитами контейнера. Медленный endpoint может ожидать базу данных, а не выполнять Python-код.

**Как это работает**

Python-профайлеры помогают выявлять дорогие пути вызовов. Runtime-инструменты показывают паттерны аллокаций, активность GC, состояние потоков и информацию об интерпретаторе. Метрики ОС выявляют ограничения ресурсов и особенности планирования, которые невозможно объяснить только Python stack trace. Поэтому важно сопоставлять трассировки, метрики процессов и телеметрию инфраструктуры.

**Пример**

Если после развёртывания выросла задержка API:

- Если трассировки показывают значительное время внутри вызова базы данных, сначала следует исследовать планы запросов, насыщение connection pool и состояние сети или базы данных, а не оптимизировать байткод Python.
- Если трассировки показывают высокую загрузку CPU на сериализации, нужно профилировать Python call path и репрезентативные payload.
- Если память контейнера растёт, а снимки Python-аллокаций остаются стабильными, следует проверить нативные расширения, memory mapping, поведение аллокатора и метрики процесса/контейнера.
- Если workers перезапускаются с OOM-событиями, необходимо проверить лимиты контейнера и память процесса до выбора способа исправления.

**Практика**

- Начинать с пользовательских симптомов и service-level indicators.
- Сопоставлять логи, метрики и трассировки.
- Сравнивать показатели с baseline.
- Использовать инструменты, соответствующие предполагаемому bottleneck.
- Воспроизводить проблему с репрезентативными данными и уровнем конкурентности.
- Разделять первопричину и сопутствующие условия.
- Проверять исправление регрессионными механизмами.

**Компромиссы**

Глубокая runtime-диагностика может выявить тонкие причины, но бывает затратной или intrusive. Sampling profilers и точечная трассировка часто безопаснее детерминированного профилирования под production-трафиком. Если тестовое окружение достаточно репрезентативно, предпочтительнее проводить intrusive-диагностику там.

**Частые ошибки**

- Начинать с анализа байткода, не установив, что проблема связана с CPU.
- Считать любое увеличение памяти утечкой Python-объектов.
- Игнорировать лимиты контейнера или задержки downstream-сервисов.
- Увеличивать число workers, не проверив память и пропускную способность зависимостей.
- Менять несколько переменных одновременно.
- Объявлять первопричину установленной только на основании корреляции.

**Senior perspective**

Senior Engineer ведёт расследование от начала до конца: формулирует проблему, выбирает уровень диагностики, объединяет данные приложения и платформы, управляет production-рисками, сообщает степень неопределённости и проверяет результат. Цель — безопасно восстановить работу сервиса и предотвратить повторение проблемы, а не продемонстрировать знание внутренних механизмов интерпретатора.

**Ответ для интервью (RU)**

«Я выбираю уровень диагностики исходя из симптома и имеющихся доказательств. Сначала определяю масштаб, временную последовательность и влияние проблемы, используя метрики сервиса, логи и трассировки. Поведение приложения я исследую, если проблема связана с бизнес-логикой, состоянием или использованием зависимостей. К диагностике Python и CPython перехожу, когда профилирование, stack traces, данные об аллокациях или особенности интерпретатора указывают на проблему runtime. Уровень ОС и контейнера проверяю при признаках ограничения CPU, лимитов памяти, OOM kill, исчерпания файловых дескрипторов, сетевых проблем или сбоев процессов.

Я не начинаю с изучения внутренних механизмов без гипотезы. Сопоставляю данные разных уровней, проверяю наиболее вероятное объяснение минимальным экспериментом, затем валидирую исправление под репрезентативной нагрузкой и добавляю мониторинг или регрессионные тесты».

# PY-002 — Что происходит при вызове функции в CPython?

**Оригинальный вопрос (EN):** What happens during a function call in CPython?

**Что проверяется**

Семантику вызова, связывание аргументов, function objects и code objects, execution frames, пространства имён, closures, возврат значений, распространение исключений и различие между контрактом Python и деталями CPython.

**Коротко**

При вызове функции Python вычисляет вызываемый объект и выражения аргументов, применяет протокол вызова и связывает позиционные и именованные аргументы с параметрами. Затем тело функции выполняется с использованием скомпилированного code object и runtime-контекста, включающего локальное состояние, globals, built-ins и closure variables, если они есть. Концептуально активный вызов представлен execution frame. Внутреннее представление frame и путь вызова в CPython менялись между версиями. Функция возвращает значение либо распространяет исключение. Вызов генераторной или coroutine-функции создаёт соответствующий объект, а не выполняет тело немедленно до завершения.

**Объяснение**

1. **Вычисление выражения вызова.** Python вычисляет вызываемый объект и выражения аргументов согласно правилам языка. Они сами могут выполнять код или возбуждать исключения до входа в тело.
2. **Протокол вызова.** Callable может быть Python-функцией, bound method, классом, встроенным объектом или экземпляром класса с __call__. Разные типы callable могут использовать разные внутренние пути.
3. **Связывание аргументов.** Позиционные и именованные аргументы, defaults, positional-only и keyword-only параметры, *args и **kwargs обрабатываются по сигнатуре. Некорректные комбинации вызывают TypeError до выполнения тела. Значения по умолчанию вычисляются при выполнении определения функции, а не при каждом вызове.
4. **Состояние выполнения.** Функции нужны локальное состояние, globals, built-ins и closure cells. Концептуально это execution frame, но нельзя утверждать, что каждый вызов всегда создаёт традиционный heap-allocated frame одним и тем же способом: внутренние механизмы CPython менялись.
5. **Выполнение тела.** Интерпретатор выполняет инструкции, разрешает имена, вызывает другие функции, управляет потоком выполнения и при необходимости переходит в native code.
6. **Завершение.** return передаёт результат вызывающему коду. Если явного return нет, функция возвращает None. Необработанное исключение распространяется к вызывающему коду.
7. **Жизненный цикл состояния.** Активное состояние после вызова больше не требуется для продолжения функции, но объекты могут оставаться достижимыми через возвращённые значения, closure или traceback. Traceback способен удерживать frames и локальные объекты, что важно при анализе утечек и удержания памяти.

Вызов — это не просто переход к другой инструкции: он включает вычисление аргументов, связывание параметров, управление контекстом, обработку потока управления и возврат результата или исключения.

**Как это работает**

- **Function object:** связывает code object с globals, defaults и информацией о closure.
- **Code object:** содержит скомпилированные инструкции и метаданные; переиспользуется между вызовами, поэтому функция не компилируется заново при каждом вызове.
- **Argument binding:** сопоставляет аргументы параметрам, применяет defaults и собирает вариативные аргументы.
- **Execution frame:** концептуально представляет активный контекст выполнения. Его внутреннее устройство — деталь реализации CPython.
- **Call protocol:** поддерживает разные категории callable; оптимизированные пути CPython не являются гарантией языка.
- **Return/exception paths:** нормальное завершение возвращает значение, исключительное — распространяет исключение и traceback.
- **Closures:** вложенная функция может удерживать переменные внешней области через closure cells.

**Пример**

~~~python
def make_multiplier(factor):
    def multiply(value, *, offset=0):
        return value * factor + offset
    return multiply

triple = make_multiplier(3)
result = triple(10, offset=2)
~~~

Вызов make_multiplier(3) создаёт вложенную функцию. Возвращённая multiply сохраняет доступ к factor через closure. Вызов triple(10, offset=2) связывает value позиционно, offset по имени, получает factor из замыкания и возвращает 32.

## Пример интроспекции

~~~python
import inspect

def describe(item, limit=10, *, strict=False):
    return item[:limit]

print(inspect.signature(describe))
print(describe.__code__.co_varnames)
print(describe.__code__.co_freevars)
~~~

inspect.signature() позволяет исследовать сигнатуру callable, если она доступна. Атрибуты code object полезны для диагностики, но не должны считаться стабильным форматом данных приложения. В этом примере co_freevars пуст, поскольку функция не захватывает переменные внешней области видимости.

**Практика**

- Делать сигнатуры явными.
- Помнить, что defaults вычисляются один раз при выполнении определения функции.
- Осознанно использовать closures и учитывать удерживаемые ими объекты.
- Обрабатывать исключения на уровне, где возможно восстановление.
- Профилировать перед изменением границ функций ради производительности.
- Предпочитать читаемую декомпозицию преждевременному объединению функций.
- Не удерживать frames и tracebacks дольше необходимого.

**Компромиссы**

Много небольших функций улучшает модульность, тестируемость и читаемость, но может добавить overhead в горячих участках. Крупные функции и inlining иногда уменьшают overhead, но ухудшают сопровождаемость; произвольный source-level inlining не гарантируется Python. Closures инкапсулируют состояние, но могут продлевать время жизни объектов. Декораторы и wrappers обеспечивают композицию, но добавляют уровни вызовов. Native callables могут иметь другие характеристики производительности, зависящие от нагрузки и версии интерпретатора.

**Частые ошибки**

- Считать, что каждый вызов заново компилирует функцию.
- Предполагать, что любой callable — обычная Python-функция.
- Считать, что Python копирует все объекты при передаче аргументов: передаются ссылки на объекты.
- Забывать, что выражения аргументов вычисляются до вызова и могут иметь побочные эффекты.
- Считать, что defaults вычисляются при каждом вызове.
- Считать frame обычным словарём со всеми локальными переменными.
- Объявлять call overhead узким местом без профилирования.
- Игнорировать traceback и closure при анализе удержания памяти.

**Senior perspective**

Для корректности важно понимать связывание аргументов, ссылки на объекты, области видимости, возврат значений и распространение исключений. Для производительности нужно измерять реалистичную нагрузку и выяснять, где расходуется время: на диспетчеризацию вызовов, тело функции, сериализацию, аллокации, I/O или downstream-сервисы. Если оптимизация зависит от внутренностей CPython, её следует изолировать, ограничить поддерживаемыми версиями и обосновать измеренным выигрышем.

**Ответ для интервью (RU)**

«При вычислении вызова Python сначала вычисляет вызываемый объект и выражения аргументов, затем применяет протокол вызова и связывает позиционные и именованные аргументы с параметрами функции. Тело выполняется с использованием скомпилированного code object и runtime-контекста, который предоставляет локальное состояние, globals, built-ins и переменные замыкания, если они есть.

Концептуально активный вызов представлен execution frame. В CPython конкретное представление frame и внутренний путь вызова относятся к деталям реализации и менялись между версиями. Функция может вернуть значение или передать исключение. Если это генераторная или coroutine-функция, вызов создаёт соответствующий объект, а не выполняет тело немедленно до завершения.

При оптимизации я сначала профилирую репрезентативную нагрузку, поскольку основная стоимость может находиться внутри функции или в I/O, а не в самом механизме вызова».

# FU-005 — Состояние выполнения при вызове функции

**Оригинальный вопрос (EN):** What execution state does CPython need to establish or maintain when entering and executing a Python function?

**Вопрос (RU):** Какое состояние выполнения CPython должен создать или поддерживать при входе в Python-функцию и во время её выполнения?

**Коротко**
CPython должен обеспечить code object, связанные аргументы, локальное состояние, globals, built-ins, closure cells и состояние управления потоком. Концептуально это execution frame. Точная структура и стратегия выделения frame — детали реализации.

**Объяснение и механика**
Function object предоставляет code object и runtime-метаданные. До выполнения тела механизм вызова связывает аргументы с параметрами. Функции нужны локальные значения, globals, built-ins, closure cells, позиция инструкции и состояние обработки исключений. Оптимизированный CPython может не материализовать полноценный Python-visible frame до необходимости интроспекции или tracing. Локальное хранилище не обязано быть обычным словарём.

~~~python
def outer(prefix):
    suffix = "!"
    def inner(name):
        return prefix + name + suffix
    return inner

greet = outer("Hello, ")
print(greet("Ada"))
~~~

inner использует собственный параметр name и свободные переменные prefix и suffix, сохранённые через closure cells после завершения outer.

**Практика и компромиссы**
Различать locals, globals, built-ins и closure variables. Frame introspection применять для диагностики, не как обязательную часть прикладной логики. Интроспекция может добавлять overhead и удерживать большие графы объектов.

**Частые ошибки**
- Предполагать, что locals всегда полностью материализованы как dict.
- Считать, что globals функции берутся из вызывающего модуля.
- Забывать, что closure удерживает внешние переменные.
- Считать, что frame выделяется одинаково во всех версиях CPython.

**Senior perspective**
При анализе удержания памяти проверять closure, traceback и сохранённые frame references. Для диагностических инструментов использовать документированные API и тестировать поддерживаемые версии CPython.

**Ответ для интервью (RU)**
«Для выполнения функции CPython необходимы её code object, связанные аргументы, локальное состояние и доступ к globals, built-ins и closure cells. Также поддерживается состояние управления потоком и обработки исключений. Концептуально это execution frame, однако внутреннее представление frame и стратегия его выделения в CPython менялись. Полноценный Python-visible frame не обязательно материализуется одинаковым способом при каждом вызове».

# FU-006 — Профилирование накладных расходов вызовов функций

**Оригинальный вопрос (EN):** How can you use profiling and call-stack information to investigate excessive function-call overhead in a Python service?

**Вопрос (RU):** Как с помощью профилирования и информации о стеке вызовов исследовать чрезмерные накладные расходы на вызовы функций в Python-сервисе?

**Коротко**
Я фиксирую репрезентативную нагрузку, измеряю baseline и использую profiler для выявления функций с большим количеством вызовов и существенным self или cumulative time. Сопоставляю профиль с traces и latency запросов, чтобы отделить Python call overhead от I/O, БД, сериализации, блокировок и native code.

**Подход**
1. Определить цель: throughput, CPU, p95/p99 latency или время конкретного endpoint.
2. Собрать реалистичные входные данные и профиль конкурентности.
3. Зафиксировать baseline: wall-clock latency, CPU time, throughput и memory.
4. Изучить call paths с помощью cProfile или sampling profiler.
5. Различать self time — время внутри самой функции — и cumulative time, включающее вложенные вызовы.
6. Сопоставить профиль с request traces и инфраструктурными метриками.
7. Проверить одну целевую гипотезу при тех же условиях.

**Механика, пример и компромиссы**
Deterministic profiling инструментирует события вызова и может искажать время. Sampling profiler периодически фиксирует состояние и обычно имеет меньший overhead, но может пропускать короткие события. Если helper вызывается миллионы раз и потребляет существенный CPU time, можно вынести повторяющуюся работу из цикла или применить batching. Если задержка приходится на БД, объединение helper-функций не решит проблему.

**Практика**
Использовать репрезентативную нагрузку, различать self/cumulative time, сопоставлять CPU profiles с traces и инфраструктурными метриками, сравнивать результаты до и после при одинаковых условиях.

**Частые ошибки**
Оптимизировать по одному call count; путать cumulative и self time; считать ожидание I/O CPU overhead; сравнивать разные workloads; удалять абстракции без измеренного эффекта.

**Senior perspective**
Оценивать вклад call overhead в latency и CPU budget, максимально возможный выигрыш и стоимость сопровождения. Если bottleneck — downstream I/O, исследовать query plans, connection pooling, batching, caching и concurrency limits.

**Ответ для интервью (RU)**
«Сначала я определяю целевую метрику и собираю репрезентативную нагрузку. Затем использую профилировщик для анализа количества вызовов, self time и cumulative time и сопоставляю результаты с трассировками. Большое количество вызовов само по себе не доказывает, что они дороги: время может уходить на БД, сеть, сериализацию или native extension. После формулирования гипотезы я вношу целевое изменение и сравниваю latency percentiles, CPU, память и корректность на той же нагрузке. Я не жертвую сопровождаемостью ради оптимизации без измеримого эффекта».

# FU-007 — Различные жизненные циклы выполнения

**Оригинальный вопрос (EN):** How do recursion, exceptions, generators, and asynchronous functions affect the execution lifecycle compared with an ordinary function call?

**Вопрос (RU):** Как рекурсия, исключения, генераторы и асинхронные функции влияют на жизненный цикл выполнения по сравнению с обычным вызовом функции?

**Коротко**
Рекурсия создаёт вложенные вызовы с отдельным логическим состоянием. Исключения передают управление через разматывание стека. Генераторная функция возвращает generator object, тело которого выполняется при итерации и сохраняет состояние между yield. Async-функция возвращает coroutine object, который выполняется при await или планировании event loop.

**Объяснение**
- **Обычная функция:** выполняется после связывания аргументов до return или exception.
- **Рекурсия:** каждый вызов имеет своё логическое состояние. Глубокая рекурсия может достичь recursion limit; общей гарантии tail-call elimination нет.
- **Исключения:** Python ищет обработчик, разматывая execution contexts. Traceback может удерживать frames и локальные объекты.
- **Генераторы:** вызов возвращает generator object; next() или итерация выполняет тело до yield, return или exception, сохраняя состояние между продвижениями.
- **Async-функции:** вызов async def создаёт coroutine object. Тело выполняется при await или scheduling; event loop управляет продвижением coroutine через точки приостановки.
- **Cancellation и cleanup:** отмена обычно доставляется в точке приостановки. Использовать try/finally и async context managers, не подавлять cancellation случайно.

**Пример**

~~~python
def ordinary():
    print("body runs during call")
    return 1

def generate():
    print("body starts on iteration")
    yield 1

async def asynchronous():
    print("body starts when awaited/scheduled")
    return 1

ordinary()
g = generate()
next(g)
coro = asynchronous()
~~~

Создание coroutine object само по себе не выполняет тело; coroutine нужно await-ить или запланировать.

**Практика и компромиссы**
Ограничивать глубину рекурсии; закрывать генераторы, владеющие ресурсами; не оставлять coroutine без await/scheduling; проектировать cleanup при cancellation; не блокировать event-loop thread. Генераторы подходят для ленивой обработки, asyncio — для I/O concurrency, но не ускоряет CPU-bound вычисления автоматически.

**Частые ошибки**
Считать, что generator body или async body выполняется немедленно; считать event loop отдельным потоком на coroutine; предполагать tail-call optimization; подавлять cancellation; удерживать tracebacks без учёта frames.

**Senior perspective**
Выбирать модель под workload и lifecycle: recursion при ограниченной глубине, generators для ленивых pipeline, coroutine для I/O concurrency, threads/processes при подходящих свойствах выполнения и изоляции. Cleanup, cancellation, backpressure и observability должны быть частью дизайна.

**Ответ для интервью (RU)**
«Обычная функция выполняется при вызове и завершается возвратом значения или исключением. Рекурсия создаёт вложенные вызовы с отдельным логическим состоянием. Исключения разматывают поток управления до нахождения обработчика. Вызов генераторной функции возвращает generator object, тело которого выполняется при итерации и сохраняет состояние между yield. Вызов async-функции возвращает coroutine object; она выполняется при await или планировании, а event loop управляет её продвижением через точки приостановки. Эти различия важны для очистки ресурсов, cancellation, глубины стека и scheduling».

# FU-008 — Когда механика вызовов важна для оптимизации

**Оригинальный вопрос (EN):** When would knowledge of CPython call mechanics materially change an optimization decision, and how would you validate that the optimization is worthwhile?

**Вопрос (RU):** В каких случаях знание механики вызовов CPython может существенно повлиять на решение об оптимизации и как проверить, что такая оптимизация действительно оправданна?

**Коротко**
Это знание важно, если profiling показывает, что Python call dispatch или повторяющиеся wrapper layers занимают существенную часть CPU-bound workload. Знание оптимизаций CPython помогает формировать гипотезы, но не заменяет измерения. Проверять результат нужно на репрезентативной нагрузке и поддерживаемых версиях.

**Объяснение**
Механика вызовов может иметь значение в горячих циклах с миллионами вызовов небольших функций, длинных цепочках wrappers/decorators, callback-heavy коде и pipeline с множеством вызовов на элемент. Однако большое число вызовов не доказывает, что dispatch является bottleneck: стоимость может приходиться на allocations, attribute lookup, преобразование данных, locks или I/O.

Возможные оптимизации: убрать лишние wrappers, перенести invariant work за пределы горячего цикла, применить batching или подходящие built-ins, сократить повторный lookup либо изменить алгоритм. Native extension или vectorized library оправданны только в подходящих сценариях.

**Проверка оптимизации**
1. Зафиксировать входные данные и конкурентность.
2. Измерить baseline повторяемыми benchmarks и production telemetry.
3. Профилем подтвердить существенность call overhead.
4. Оценить верхнюю границу возможного выигрыша.
5. Внести одно целевое изменение.
6. Выполнить correctness, edge-case и regression tests.
7. Проверить все поддерживаемые версии Python и deployment configurations.
8. Сравнить p50/p95/p99 latency, throughput, CPU, memory и сложность сопровождения.
9. Оставить оптимизацию, только если выигрыш оправдывает её стоимость.

**Механика и компромиссы**
CPython меняет call paths и оптимизации, включая specialization, vectorcall-related mechanisms и frame optimizations. Это детали реализации. Inlining может снизить overhead, но ухудшить тестируемость; batching снижает количество вызовов и I/O, но увеличивает память или задержку отдельного элемента; native code ускоряет CPU-bound операции, но усложняет сборку, ABI, debugging и deployment.

**Частые ошибки**
Оптимизировать по интуиции или одному microbenchmark; считать оптимизации одинаковыми во всех версиях; игнорировать алгоритмическую сложность; жертвовать читаемостью ради малого ускорения; измерять только среднюю latency; не повторять benchmark после обновления runtime.

**Senior perspective**
Низкоуровневая стоимость должна быть связана с измеримым результатом сервиса. Если dispatch занимает значительную часть CPU budget горячего пути, уменьшение лишних вызовов может быть оправданно. Если его вклад в end-to-end latency мал, следует сохранить чистые абстракции и работать над реальным bottleneck. Документировать доказательства, версии runtime, ожидаемый эффект и rollback criteria.

**Ответ для интервью (RU)**
«Я оптимизирую механику вызовов только после того, как профилирование показывает, что диспетчеризация Python-вызовов или повторяющиеся слои обёрток существенно влияют на репрезентативную CPU-bound нагрузку. Я анализирую self time и call paths, оцениваю максимально возможный сквозной выигрыш и проверяю целевой вариант, например устранение лишних вызовов или пакетную обработку. Затем сравниваю корректность, перцентили latency, throughput, CPU, память и сопровождаемость на поддерживаемых версиях Python. Оптимизации вызовов в CPython меняются со временем, поэтому я не полагаюсь на приватные внутренние механизмы без изоляции и измеренного обоснования».

# PY-003 — Основной вопрос

**Вопрос (RU):** Объясните объектную модель Python: идентичность, тип и значение объекта.

**Оригинальная формулировка (EN):** Explain Python's object model: identity, type, and value.

**Что проверяется:** Связывание имён с объектами, различие идентичности и равенства, изменяемость, проверки типов и проектирование API.

У каждого объекта Python есть идентичность, тип и значение. Идентичность отличает конкретный объект; тип определяет его поведение и поддерживаемые операции; значение представляет данные или состояние. Идентичность и тип остаются постоянными в течение жизненного цикла объекта, а значение может изменяться, если объект изменяемый.

Переменная — это имя, связанное с объектом, а не типизированная ячейка хранения. Присваивание обычно связывает имя с объектом, а не копирует его. Поэтому несколько имён могут ссылаться на один изменяемый объект.

~~~python
first = [1, 2]
alias = first
another = [1, 2]

first is alias       # True: один объект
first == another    # True: значения равны, объекты разные

alias.append(3)     # Изменение видно и через first
~~~

Используйте is для проверки идентичности, например при сравнении с None или отдельным sentinel-объектом; == — для сравнения значений. isinstance() подходит, когда допустимы подклассы. Если важнее поведение, чем конкретная реализация, предпочтительнее протоколы и полиморфизм.

Не путайте идентичность Python-объекта с доменной идентичностью. Два ORM-экземпляра могут представлять одну строку БД, оставаясь разными объектами Python. Для persistence, сериализации и распределённых систем используйте стабильные доменные идентификаторы. Значение id() действует только в течение жизненного цикла объекта и не является постоянным ключом или переносимым адресом памяти.

**Ответ для интервью (RU)**

«У каждого объекта Python есть идентичность, тип и значение. Идентичность показывает, о каком конкретном объекте идёт речь, тип определяет его поведение, а значение представляет данные или состояние. Имена связываются с объектами, поэтому несколько имён могут ссылаться на один объект. Значение изменяемого объекта может меняться без изменения его идентичности и типа; повторное связывание имени отличается от мутации объекта. Я использую is для проверки идентичности, например при сравнении с None, а == — для сравнения значений. Обычно предпочитаю isinstance(), если допустимы подклассы, и протоколы, если проектирование должно зависеть от поведения. Для persistence и распределённых систем использую явные доменные идентификаторы, а не идентичность Python-объекта».

## FU-011 — Почему is не подходит для сравнения значений

**Вопрос (RU):** Почему использование is для сравнения строк, чисел и других значений может приводить к ненадёжным результатам?

**Оригинальная формулировка (EN):** Why can using is to compare strings, numbers, or other values produce unreliable results?

**Объяснение:** is проверяет, ссылаются ли выражения на один объект, а не сравнивает значения. Равные значения могут находиться в разных объектах. CPython иногда повторно использует или интернирует неизменяемые объекты, из-за чего неправильное сравнение по идентичности может случайно работать в конкретном контексте. Это оптимизация реализации, а не гарантия языка.

**Ответ для интервью (RU)**

«is проверяет идентичность объекта, а == — равенство согласно правилам сравнения конкретного типа. Два независимо созданных значения могут быть равны, не являясь одним объектом. Интернирование или повторное использование констант иногда создаёт впечатление, что сравнение через is работает для строк или чисел, но это зависит от реализации. Для sentinel-объектов я использую is, а для сравнения значений — ==».

## FU-012 — Идентичность и изменяемость при проектировании API

**Вопрос (RU):** Как при проектировании API избежать случайной зависимости от идентичности объектов, их изменяемости или конкретных типов реализации?

Требуемое поведение лучше выражать через протоколы и абстракции, а внешние данные валидировать и нормализовать на границах системы.

**Ответ для интервью (RU)**

Для persistence и распределённых границ я использую стабильные доменные идентификаторы, а не идентичность Python-объекта. Неизменяемые value objects полезны, когда семантика основана на значениях, при условии корректной обработки вложенного состояния и хеширования.
